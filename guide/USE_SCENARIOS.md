# Use Scenarios

hd-lang is designed around two primary scenarios:

1. interactive scripts and typed tool calls inside AI agents;
2. engineering and infrastructure code generated by AI and reviewed by humans.

This document records product requirements and design fit. It is not a second
language specification. Accepted syntax and semantics live in the
[formal specification](../spec/README.md), while unresolved work lives in
[Open Issues](../future-work/OPEN_ISSUES.md).

## Scenario 1: Interactive Scripts And AI-Agent Tool Calls

The language should make short scripts easy to write while keeping tool inputs,
dependencies, authority, failures, and runtime behavior visible to both agents
and human reviewers.

### Typed Data, Schemas, And Validation

Typed data should replace loose JSON at tool boundaries. The language and its
libraries should support:

1. structured tool input and output types;
2. input validation and sanity checks before execution;
3. output validation after execution;
4. shared types referenced across files and tools;
5. field-level validation and composable validators;
6. custom validators written as ordinary functions;
7. lightweight member metadata and richer `annotate Validation for Target`
   derivation;
8. generated JSON Schema, OpenAPI, MCP descriptions, TypeScript definitions,
   and documentation for external ecosystems.

Validation metadata does not create a distinct static subtype. Domain identity
uses an ordinary nominal type; annotations attach validation or presentation
information to that type.

### Tool Interfaces And Registration

Tools should remain ordinary typed functions with library-defined metadata,
not loose wrappers or a separate declaration kind. A tool interface should
describe:

1. input and output types;
2. explicit `Result` error behavior;
3. human-readable and machine-readable descriptions;
4. dependency and capability requirements;
5. authentication and access-control metadata;
6. examples and references to related tools;
7. generated external specifications;
8. explicit runtime registration.

```text
trait Database:
    fn get_user!(self, id: UserId) -> Result[User, ToolError]

fn get_user!(id: UserId) -> Result[User, ToolError] $ Database:
    db := $.use(Database)
    Ok(db.get_user!(id)?)

annotate Tool for get_user: pass
tool_registry.register(Tool::annotation(get_user))
```

The same registration model should extend to service endpoints, jobs,
workflows, and host-callable Wasm functions.

### Dependencies, Capabilities, And Sandboxing

Requirement rows and provider contexts should make tool dependencies and
authority visible. They should support:

1. database, network, clock, filesystem, secret, subprocess, authentication,
   and other explicit requirements;
2. compiler verification that every required provider is available;
3. test, mock, production, and restricted provider implementations;
4. capability checks before tool execution;
5. generated dependency and capability reports;
6. sandboxed execution by default;
7. higher-order functions that propagate row parameters and remove
   requirements they satisfy locally;
8. interactive resumption without silently gaining new authority.

Normal errors use `Result`; requirements describe dependencies; `fn!` and
`Suspend[T]` describe one-shot suspension. These mechanisms replace the older
single “effects and handlers” model.

### Testing And Repair Diagnostics

Agent tooling should be able to exercise tools over generated inputs and
produce repairable failures. It should support:

1. unit-test blocks and ordinary `std.testing` assertions;
2. generated valid inputs from types and annotation metadata;
3. checked examples attached to tool metadata;
4. mocked providers;
5. reproducible property-test failures and shrinking;
6. structured, machine-readable diagnostics;
7. source links from failures to declarations and metadata.

Invalid-input generation is useful for negative testing but is not an initial
requirement.

### Interactive Execution And Observability

Interactive runs should combine notebook-style recovery with controlled
observability. They should support:

1. resuming an interrupted session;
2. preserving typed values and validated data where possible;
3. intentionally rerunning or skipping previous steps;
4. recording which requirements and capabilities were used;
5. inspectable execution history for agents and humans;
6. logs, traces, metrics, and structured diagnostics;
7. links from runtime events to source declarations;
8. redacted, access-controlled inspection without raw production-data access.

### Serializable Computation And Incremental Reuse

Serializable closures should let tools package computation as well as data.
They should preserve code identity, serializable captured values, dependency
requirements, and authority boundaries when stored, moved, cached, or resumed.

Incremental computation should avoid repeating expensive work when only part
of an input or environment changes. It should provide dependency-aware cache
keys, reuse intermediate results, invalidate on changes to inputs, captures,
dependencies, or code, and explain cache hits and misses.

## Scenario 2: AI-Generated Engineering And Infrastructure

The language should make generated systems reviewable, testable, auditable,
deployable, and operable without granting an agent uncontrolled production
access.

### Reviewable Errors And Dependencies

Generated code should expose important obligations at its boundaries:

1. expected failures appear in `Result` types;
2. unhandled errors are rejected;
3. dependencies appear in requirement rows;
4. missing providers are rejected;
5. callback requirements propagate through explicit row parameters;
6. error and requirement paths remain readable during review;
7. diagnostics provide structured context for automated repair;
8. dependency and capability graphs can be generated for audit.

Function contracts and type invariants are outside the language. Preconditions,
postconditions, and output checks should instead use types, validation,
ordinary functions, tests, and structured runtime diagnostics.

### Data Models And Lifecycle Metadata

Typed data definitions should support:

1. field-level validation and Zod-like validator composition;
2. custom validation functions;
3. schema-driven property-test data generation;
4. serializer and deserializer generation;
5. database, UI, documentation, and observability facets;
6. declarative retention, archive, anonymization, and cascade-deletion policy;
7. lifecycle checking against concrete storage backends;
8. links from runtime values and operational signals back to source types.

Schema, validation, persistence, UI, and lifecycle descriptions should share
the general annotation model rather than introduce separate declaration
systems.

### Correctness And Property Testing

Correctness tooling should be part of ordinary development:

1. built-in `test` blocks and `std.testing` assertions;
2. dependency injection through requirement traits and provider contexts;
3. property testing implemented as a `std.testing` library;
4. generated data derived from types and metadata;
5. reproducible seeds and failure artifacts;
6. shrinking of failing cases;
7. integration with mock providers;
8. machine-readable reports that agents can use to repair code.

### Observability And Controlled Inspection

Generated systems should expose:

1. logs, traces, and metrics;
2. structured operation context;
3. workflow and replay history;
4. correlation between test, validation, runtime, and workflow failures;
5. source mappings from runtime events to declarations;
6. query tools with redaction and access-control enforcement;
7. visible cache invalidation and recomputation;
8. controlled operational examples without unrestricted raw-data access.

### Durable Workflows And Recovery

Durable workflows should be runtime and standard-library facilities built on
one-shot suspension, explicit requirements, and deterministic replay. They
should support:

1. durable progress and persisted state;
2. retry policy and idempotency boundaries;
3. resumption after interruption, crash, retry, or deployment;
4. mocked external dependencies in tests;
5. observable execution history;
6. capability-stable recovery;
7. compensation or cleanup policies;
8. integration with observability and data-retention rules.

Interactive session recovery and durable workflow replay share infrastructure
but have different semantics. Tooling must clearly distinguish replayed work
from newly executed external actions.

### Serializable Closures

Serializable closures should support durable workflows, remote execution, and
caching. They require:

1. stable code identity and captured-value encoding;
2. validation that every captured value is serializable;
3. preservation or explicit rebinding of requirements and capabilities;
4. deterministic behavior between recorded suspension points;
5. safe movement across runtime boundaries without ambient authority;
6. compatibility and migration checks when code changes.

Durable workflow recovery replays from recorded events; it does not imply that
the runtime serializes an arbitrary machine stack.

### Incremental Computation

Incremental computation should support:

1. tracked dependencies between computations and data;
2. recomputation of only affected outputs;
3. cache keys incorporating code identity, arguments, and captured values;
4. explicit versioning for external inputs;
5. integration with interactive sessions and durable workflows;
6. visible invalidation and recomputation traces;
7. explainable cache hits and misses;
8. separation between cache reuse and deterministic workflow replay.

### Infrastructure Awareness

Infrastructure support should let code and controlled operational context
explain a system without embedding raw provider configuration into core syntax.
It should support:

1. models of deployed resources and runtime dependencies;
2. resource definitions derived from code where practical;
3. explicit registration and deployment metadata;
4. deployment or synchronization through provider adapters;
5. connections from source to logs, traces, metrics, schemas, and examples;
6. access-control wiring and review;
7. inspection by agents without bypassing authentication or privacy policy.

### Declarative Data Retention

Retention uses the annotation model rather than standalone syntax:

```text
data User:
    id: UserId
    deleted: bool

data Post:
    id: PostId
    userId: UserId

annotate Post:
    userId = [retention_owner(shape(User)), delete_when(shape(User.deleted))]

annotate Retention for Post: pass
```

An ownership marker alone is insufficient; metadata must state the lifecycle
policy. A retention library can derive the complete policy, validate it against
storage adapters, generate tests and operational checks, and coordinate
deletion with workflows, audit logs, and access control.

## Cross-Scenario Design Boundaries

The two scenarios share these accepted directions:

1. schemas are derived from ordinary data, enum, function, and annotation
   declarations rather than a parallel schema language;
2. validation metadata does not silently refine static types;
3. custom validators are ordinary functions;
4. annotations support validation, database, UI, retention, observability, and
   other library-defined facets;
5. tools, endpoints, jobs, and workflows are ordinary functions with explicit
   metadata and registration;
6. errors, dependencies, and suspension remain separate as `Result`,
   requirement rows and provider contexts, and `fn!`/`Suspend[T]`;
7. function contracts, invariants, and a dedicated concurrency construct are
   not core language features;
8. workflows, property testing, serializable closures, incremental computation,
   and infrastructure integration are library, tooling, or runtime designs;
9. sandbox authority comes from explicit providers at the Wasm host boundary;
10. observability and operational access must preserve privacy, redaction, and
    authorization.

## Tooling Requirements

A complete ecosystem for these scenarios needs the following tool families.
The list describes desired capabilities, not separate language constructs.

### Schema, Validation, And Documentation

- schema and type checking;
- validator generation and composition;
- JSON Schema, OpenAPI, MCP, and typed-client generation;
- serializer and deserializer generation;
- test-data and documentation generation;
- lifecycle and retention checking.

### Requirements, Capabilities, And Sandboxing

- requirement-row and provider-context checking;
- row-polymorphism checking, including explicit requirement removal;
- mock-provider generation;
- dependency graph and capability audit reports;
- sandbox policy and host-capability checking;
- sandboxed runners for interactive and production entry points.

### Testing And Diagnostics

- property-test running, reproducible failure artifacts, and shrinking;
- generated valid inputs and optional negative-test generation;
- mock-provider integration;
- structured validation, test, and runtime diagnostics;
- source-linked reports suitable for automated repair.

### Registration And Deployment

- registration scanning and runtime registries;
- tool and service graph generation;
- access-control checking;
- external specification generation;
- deployment and synchronization adapters.

### Observability

- trace, log, and metric APIs;
- source mapping from runtime events to declarations;
- controlled query and inspection tools;
- privacy, redaction, and access-control integration.

### Workflows And Resumption

- workflow and deterministic-replay checking;
- idempotency linting;
- workflow test runners and history viewers;
- interactive session and durable event stores;
- replay, resumption, and capability diagnostics;
- local, cloud, and Wasm runtime adapters.

### Serializable Closures And Incremental Computation

- closure capture and serializable-value analysis;
- code identity and hash generation;
- requirement and capability capture reports;
- runtime-boundary and compatibility checking;
- dependency graph construction and cache-key generation;
- invalidation checking and incremental recomputation planning;
- cache, recomputation, and replay inspection tools.

Specific unresolved APIs and sequencing choices are maintained only in
[Open Issues](../future-work/OPEN_ISSUES.md).
