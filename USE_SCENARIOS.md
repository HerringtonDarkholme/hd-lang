# Use Scenarios

## Scenario 1: Interactive Scripts And AI-Agent Tool Calls

The language should work well as an interactive scripting and tool-call language inside AI agents.

### Data Types For Validation And Sanity Checks

The language should make data shape explicit and easy to validate.

Requirements:

1. Define structured data types for tool inputs and outputs.
2. Attach validation rules to data types and fields.
3. Support custom validation creators.
4. Import data types from other files.
5. Reuse shared data definitions across multiple tools.

### Tool Call Interfaces

Tool calls should remain ordinary functions with typed library metadata, not
loose JSON wrappers or a separate language declaration kind.

When using this language's own infrastructure, tool declarations should replace external JSON schema/OpenAPI-style specs. When interoperating with existing tooling, the compiler should generate those specs from source.

The language should stay function-first. `annotate Tool for function` produces tool information for a normal function, and user code registers that information explicitly instead of declaring a separate top-level tool construct.

Agent scripts and tool calls should run in a sandbox by default. Access to filesystem, network, auth context, databases, secrets, clocks, subprocesses, and other external resources should be represented as explicit capabilities.

Requirements:

1. Define typed tool inputs and outputs.
2. Define explicit error behavior.
3. Include human-readable and AI-readable descriptions.
4. Include context requirements.
5. Include auth requirements.
6. Include access-control rules.
7. Support references between RPC tools.
8. Derive required capabilities from each entry point's transitive `$` requirement row.
9. Support sandboxed execution.
10. Support interactive execution resumption, similar to IPython or notebook sessions.

### Possible Tool Shape

```text
fn get_user!(id: UserId) -> Result[User, ToolError] $ Database:
    db := $.use(Database)
    user := db.get_user!(id)?
    user

annotate Tool for get_user: pass
tool_registry.register(Tool::annotation(get_user))
```

Open design areas:

1. Exact `Tool` information and explicit registry API for registering tools.
2. How access-control metadata composes with ordinary context requirements.
3. How references between tools should be declared and validated.

## Scenario 2: Engineering And Infrastructure Code Generated By AI

The language should also work as an engineering and infrastructure language where AI generates, modifies, tests, and operates real systems.

### Compiler-Verifiable Error Handling

Error handling should be clear, lexical, and compiler-verifiable.

Requirements:

1. Error behavior should be visible in function signatures or nearby declarations.
2. Unhandled errors should be rejected by the compiler.
3. Error handling should be easy for AI agents to repair.
4. Error paths should be readable during code review.

### Built-In Correctness Tools

The language should make correctness tools part of normal development.

Requirements:

1. Built-in unit-test blocks and `std.testing` assertions.
2. Mocking and dependency injection through requirement traits and provider contexts.
3. Property-based testing and generated data as a future `std.testing` library.
4. Automatic test-data derivation from types and annotation metadata.

Function contracts and invariants are explicitly outside the language.

### Built-In Observability

Observability should be part of the language model, especially for AI operations.

Requirements:

1. Logging.
2. Tracing.
3. Metrics.
4. Structured operation context.
5. AI-readable runtime diagnostics.
6. Links from runtime signals back to source-level intent.

### Durable Workflows And Persistence

The standard library should manage persistence and durable execution in the style of Vercel workflows or Temporal, built on one-shot suspension, explicit requirements, and deterministic replay.

Requirements:

1. Durable steps.
2. Retry policy.
3. Idempotency.
4. State persistence.
5. Workflow resumption.
6. Observable workflow history.
7. Capability-aware workflow execution.
8. Resumable execution after interruption, crash, retry, or deployment.

### Sandboxed And Resumable Execution

The runtime should support two related execution modes:

1. Interactive resumption for agent scripts, similar to IPython/notebook workflows.
2. Durable resumption for workflows, similar to Vercel workflows or Temporal.

Sandboxing and capabilities should be part of both modes. Resumed execution should not silently gain new access to resources.

Requirements:

1. Statically derived requirement rows for authority-bearing providers.
2. Provider implementations for tests, mocks, and production.
3. Resumable execution state.
4. Structured execution history.
5. Clear boundaries between replayed steps and newly executed steps.
6. Diagnostics that help AI agents understand what can be resumed safely.

### Serializable Closures And Incremental Computation

The runtime should support serializable closures and incremental computation as runtime features.

Serializable closures package a function reference with its captured environment so computation can be stored, moved across runtime boundaries, cached, or resumed. Captured values must be checked for serializability, requirements, and authority-bearing resources.

Incremental computation tracks dependencies between inputs, captured values, data reads, code identity, and outputs so the runtime can reuse cached results and recompute only affected work.

Requirements:

1. Code identity for serializable functions and closures.
2. Capture analysis for closed-over values.
3. Requirement and authority preservation across serialization or rebinding.
4. Dependency-aware cache keys.
5. Cache invalidation when inputs, captures, dependencies, or code change.
6. Integration with interactive sessions and durable workflows.
7. Observable cache/recompute traces for AI agents and human reviewers.

### Infrastructure Awareness

Infrastructure awareness should be built into the language so AI agents can use code inspection and operational context to understand behavior. The language should not provide raw production data access. Observability signals such as logs, traces, and metrics should be available through controlled runtime/language features.

Requirements:

1. Model deployed resources.
2. Model runtime dependencies.
3. Derive resource definitions from code where possible.
4. Deploy or sync derived resources to cloud infrastructure.
5. Connect source code to logs, traces, metrics, schemas, and operational examples.
6. Let AI agents inspect operational context without bypassing auth or privacy rules.

### Declarative Data Retention

Data types should be able to express retention, deletion, and cascade requirements declaratively.

This behavior should not be a hardcoded built-in policy. Instead, the language should provide a way to express domain-specific lifecycle requirements.

Retention should use the general annotation model, not a standalone `retention` syntax.

Open library sketch using the accepted annotation layers:

```text
data User:
    id: UserId

data Post:
    id: PostId
    userId: UserId

annotate Post:
    userId = [retention_owner(User), delete_when(User.deleted)]

annotate Retention for Post: pass
```

An ownership marker alone is not enough; the metadata must also express the
deletion policy. The concrete values above are placeholders implementing the
appropriate field-metadata trait. `Retention` derives the complete policy from
that member metadata. This is a library design, not new retention syntax.

Open design areas:

1. The concrete `FieldMetadata[UserId]` values supplied by the retention library.
2. Which policies are needed, such as delete-when, retain-for, archive-when, or anonymize-when.
3. How retention rules are checked against storage backends.
4. How deletion cascades interact with workflows, requirements, audit logs, and access control.
5. Whether retention rules generate tests and operational checks.

Infrastructure open design areas:

1. What infrastructure concepts belong in the language versus external configuration.
2. How much observability is automatic versus explicitly declared.
3. How durable workflows interact with requirements, providers, suspension, and tests.
4. How code-derived infrastructure is deployed and synced to cloud providers.
