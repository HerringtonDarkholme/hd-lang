# Compiler Profile: `b4c14e39`

Date: 2026-10-07

This report profiles repository foundation commit `b4c14e39`. Its latest
compiler-crate change is `b87eb2da`, which adds the complete architecture task
graph, validation-stage counts, and remaining embedding crates. It compares
the same generated workload with `b89ceffe`.

## Scope And Method

The release `hd_driver` benchmark ran 200 functions per folder (3,009 lines)
and 2,000 per folder (30,009 lines). Each process measured cold, warm,
all-private-body-edit, and comment-edit builds in one in-memory cache. The new
external harness under `compiler/bench/profile-signature/` measured a public
signature edit and its caller update against the same cold cache.

The release `hd` binary ran all six compiler samples, the four hand-written Q4
benchmarks, and the generated 10,000-line multi-folder package on V8 through
Node. Times are medians of five runs after one warm-up. `hd build` compiled the
trait sample without starting Node.

Samply successfully captured 170 samples after receiving profiling permission,
but the release binary exposed only addresses. Named-function samples are
therefore **no data**. The hot-function ranking maps the driver's built-in
stage timers to their owning functions, as in the preceding reports. `Parse`
is nested inside its owning stage, so those percentages overlap. Allocation
counts and peak RSS are also **no data** because neither the compiler nor the
available profile exposed them.

## Findings

1. No atrocious performance problem appears. All requested edit paths remain
   sublinear over the measured 10× source increase, and 30k cold stays below
   75 ms.
2. The architecture stages added by `b87eb2da` are measurable only in
   microseconds on this workload. Their richer task graph did not cause the
   small-input percentage changes to scale up.
3. Signature invalidation is broad where required but code reuse is narrow:
   both modules recheck, while only the changed function and caller re-emit.
4. Warm work is still dominated by `skim`. The next meaningful implementation
   fix is the manifest/`pkgres` no-edit fast path, not micro-tuning.
5. Samply now records successfully, but named samples require a symbol-bearing
   profiling build. Allocation counters remain the other measurement gap.
