# Compiler Profile: `84e1d32b`

Date: 2026-10-07

This is the first profile report for the Rust walking skeleton. The profiled
compiler commit is `84e1d32b` (`Walking skeleton: clippy fixes in hd_walk
check.rs`), running the release `hd-walk` binary on the local arm64 Mac. There
is no earlier Rust-compiler report to compare against.

## Scope And Method

`hd-walk bench 200` generated 3,009 lines and `hd-walk bench 2000` generated
30,009 lines. Each invocation used one in-memory cache for its cold, warm,
body-edit and comment-edit runs. The body edit deliberately changes the body
of every generated function in `geo`, not one function. V8 ran the emitted
Wasm through Node, which is the primary engine for this Wasm-first slice.

`samply` was installed but could not record this process (`Unknown(1100)`).
macOS `sample` was also denied permission to inspect it. The hot-function
ranking therefore maps the driver's built-in stage timers to the function
that owns each task. `Parse` is timed both inside the caller and separately,
so those rows overlap and their percentages must not be added. Allocation
counts and peak RSS were not measurable: the compiler has no allocation
counters, and `/usr/bin/time -l` could not read the required system data in
this environment.

The current harness has no signature-edit phase. It also has no `hd build`
command. Running the repository's `examples/core.hd` through `hd-walk run`
stopped at unsupported slice syntax (`$ Console`) and the unknown `Console`
name, so no misleading sample timing is reported.

Cold compilation scales close to linearly: 10 times the source is 9.1 times
the wall time and 10.0 times the Wasm size. Warm, body-edit and comment-edit
times scale by 9.4, 10.1 and 9.5 times respectively. Nothing is
order-of-magnitude or superlinear at the requested sizes.

The cache decisions are correct for the cases the harness has: a warm run
checks and emits nothing; the all-body edit checks only `pkg.geo.shapes` and
emits 2,000 of 4,001 instances; the comment edit still reparses and rechecks
that module but emits nothing and hits the link entry. A signature-edit
result is **no data** because that case is absent from the harness.

## Findings

1. No atrocious scaling problem appears at 3k or 30k lines. Cold compilation
   is under 100 ms at 30k lines on this synthetic subset.
2. The clearest avoidable cost is the missing warm no-edit fast path. At 30k
   lines, module prep plus skim account for 14.53 of 16.31 ms even though all
   semantic and link entries hit. Implement the manifest/`pkgres` path from
   Detailed Design §1.4 before tuning parser or emitter internals.
3. Comment edits correctly reuse emitted code and the linked Wasm, but still
   spend 38.39 ms reparsing and rechecking a 15k-line module. This is the
   expected whole-module tradeoff recorded in Cache §5.9, not a surprise
   regression.
4. V8 instantiation remains below 1 ms at 30k lines. Runtime grows from 1.54
   to 26.14 ms because the generated `main` executes 10 times as many calls;
   this benchmark is not a runtime-throughput comparison against Node.
5. The profiling gaps are concrete: add signature-edit timing to `hd-walk
   bench`, add the real sample/build path when its syntax is supported, and
   add allocator/RSS counters. These are harness gaps, not reasons to tune
   the current compiler.
