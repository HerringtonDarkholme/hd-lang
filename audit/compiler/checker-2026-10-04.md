# Current Compiler: Checker Analysis

Status: observational audit at `caac922a`, 2026-10-04. Nothing here is accepted behavior or an owner decision.

Scope: every module in [src/checker](../../src/checker/), with detailed inspection of orchestration, body checking, inference, rollback, derivation, and HIR construction. References: [types](../../spec/lang/04-type-system.md), [functions](../../spec/lang/07-functions.md), [traits](../../spec/lang/09-traits.md), [modules](../../spec/lang/10-modules.md), [requirements](../../spec/lang/11-requirements-and-suspension.md), and [annotations](../../spec/lang/14-annotations.md).

The checker occupies 34,522 lines across 95 files. Its public entry is `check(Program, CheckOptions)` through [index.ts](../../src/checker/index.ts).

## Pass Order

The ordering below comes from [program.ts](../../src/checker/program.ts), not a proposed replacement pipeline.

| Order | Work | Product or dependency |
| --- | --- | --- |
| 1 | Validate std uses | Invalid imports stop preparation immediately. |
| 2 | Expand `@error` | Ordinary declarations and generated implementations, before decorator name resolution. |
| 3 | Resolve bare marker calls and function-type constructors | Normalized AST; malformed function types stop checking. |
| 4 | Load std and inspect/derivation support | One joined declaration set, import aliases, test-runner identities. |
| 5 | Expand typed derivation | Generated functions, implementations, tuple instances, facts, and diagnostic origins. |
| 6 | Mark suffix functions | Literal suffix/prefix facts from surviving declarations. |
| 7 | Rename method binders and hoist local declarations | Distinct binder spellings and top-level representations of local types/implementations. |
| 8 | Check decorator targets | Runs before newtypes become data types. |
| 9 | Fill written generic defaults | Runs before aliases expand; a failure stops later semantic work. |
| 10 | Expand type/row aliases and lower newtypes | Prepared `Program` plus retained type declaration information. |
| 11 | Initialize map-key facts and program context | Per-program registries plus a module-global map-key table. |
| 12 | Validate declarations and create nominal types | Data and enum bodies, then variance checks and trait bodies. |
| 13 | Validate host capabilities and implementations | Method declarations, overlap checks, ownership, associated types, delegation, supertraits. |
| 14 | Check defaults and embedding | Generic default bounds and promoted-member constraints. |
| 15 | Synthesize callable declarations | Defaults, constructors, implementation methods, tests, module initialization. |
| 16 | Build signatures | Callable indices, generic bounds, result types, parameters, requirement rows. |
| 17 | Infer omitted signatures and check bodies | Typed functions, closures, globals, calls, coercions, dictionary plans. |
| 18 | Validate inferred variance and module initialization | Whole-program checks after bodies exist. |
| 19 | Convert captured mutable storage | Shared cells and rewritten reads/writes in the final HIR. |
| 20 | Remap and deduplicate derivation diagnostics | Public result diagnostics naming user opt-ins or members. |

Several transitions have early exits. In particular, missing mandatory result types and signature errors prevent body checking.

The std preparation sequence has a small dependency fixed point. Inspect can contain derivations, while derivation support imports inspect; idempotent loads prepare both before expansion.

The phases exchange variants of the same `Program` structure. Their invariants are primarily comments and ordering, rather than distinct types for each phase.

## Body Checker Composition

The class chain below is base-to-derived. Every stage shares one `CheckerContext` object and its inherited mutable state.

This is a dependency/inheritance listing, not hd code.

[checker.ts](../../src/checker/checker.ts) supplies expression dispatch, contextual hints, coercion, closure checking, and literal retry. The inherited classes supply cases that call back into those operations.

File boundaries improve navigation, but do not isolate execution state. Changing a common helper can affect every expression family in the chain.

### Function State

[context.ts](../../src/checker/context.ts), `CheckerContext`, takes 21 constructor parameters, including optional ones. They describe declaration inputs, registries, flags, captures, providers, closures, imports, globals, and local implementations.

| State | Ownership | Consumers |
| --- | --- | --- |
| Type and trait registries, implementations, signatures | Program inputs to each function checker | Type resolution, member selection, generic obligations. |
| Lexical scopes and locals | Function checker | Binding, shadowing, reads, mutation, patterns, synthetic temporaries. |
| Provider scopes and inferred requirements | Function checker | Requirement lookup, closures, row inference. |
| Captures and shared closure output | Function checker plus enclosing compilation | Closure construction, nested checking, later cell conversion. |
| Globals | Shared compilation map | Module body populates it before ordinary bodies. |
| Prechecked expression cache | Inherited checker state | Spread rewrites and avoiding duplicate checking of rewritten expressions. |
| Inference flags and transient contextual hints | Function checker | Result/row inference, contextual closure types, generic calls. |
| Diagnostics and panic-detail marker | Function checker | Failure handling and final program/runtime metadata. |

Local implementation scopes filter the full implementation list at lexical activation points. Hoisting therefore does not by itself make every local implementation visible everywhere.

`HirLocal` object identity matters. Scopes, capture sources, and warning collection refer to local objects, and speculative rollback must preserve existing identities.

[capture-view.ts](../../src/checker/capture-view.ts) supplies a live view of enclosing captures, lexical scopes, and provider bindings. It replaces full merged-map copies for each closure while preserving lookup precedence.

That view is another shared-state contract: lookup observes its referenced scopes, while iteration deduplicates names and returns their winning bindings. It is included in this audit's final frozen revision.

## Types, Inference, And Obligations

### Type Representation

[hir.ts](../../src/hir.ts) defines `ValueType` as `string`. Formats include nominal applications, tuple and function types, permission prefixes, generic binders, trait views, provider rows, and suspension identities.

[types.ts](../../src/types.ts) decomposes and reconstructs these strings. [shared.ts](../../src/checker/shared.ts) adds semantic resolution, generic substitution, requirement-row matching, and implementation matching.

This permits readable dumps and direct string equality. It also makes canonical spelling and repeated parsing part of the correctness and cost model.

Written types are validated through both `shared.typeName` and `CheckerContext.resolveType`. They share some validators, but retain separate orchestration and a top-level `Map` key special case.

The existing O-03 written-constructor-bound issue remains visible in these paths. This audit inspected the mechanism but did not rerun the older hd reproduction.

### Signature Inference

[program-inference.ts](../../src/checker/program-inference.ts) separates two mechanisms. Omitted results are inferred lazily on signature lookup; omitted private requirement rows grow until a fixed point.

`LazySignatures.get` may run another function checker. It is therefore an effectful lookup, with possible signature replacement, diagnostics, and failure-state changes.

An inference stack detects recursive result inference and reports `recursive-function-needs-result-type`. Explicit result types avoid that result dependency cycle.

Row inference starts from empty rows and repeatedly checks the relevant declarations. A round also rebuilds globals from the module body when one exists.

Rows grow by set union and are sorted. The implementation scans row declarations each round rather than scheduling only callers whose dependencies changed.

Final body checking runs after inference. Consequently, one function can be checked during lazy result inference, during row rounds, and again for final HIR.

### Generic Calls

[calls.ts](../../src/checker/calls.ts), `checkSignatureArguments`, combines argument planning and solving. It handles explicit type/row arguments, expected-result hints, tuple spreads, named arguments, varargs, defaults, bounds, and substitutions.

Arguments are generally checked in source order. [literal-arguments.ts](../../src/checker/literal-arguments.ts) postpones unresolved numeric literals when a later argument can determine their type.

[bound-inference.ts](../../src/checker/bound-inference.ts) propagates solutions from a known receiver's trait instantiation. It repeats until no parameter solution changes.

Trait calls may use concrete implementation functions, dictionaries for generic bounds, or dynamic trait values. HIR records the chosen function indices and dictionary plans, reducing backend name resolution.

Associated calls and member calls use related but separate selection paths. Both can trial-check competing instantiations of the same generic trait.

### Coercion And Joins

The checker distinguishes ordinary assignment compatibility, permission weakening, declared variance, row subsumption, literal adaptation, and least-common-type selection. They are not one universal conversion operation.

`least-common-type.ts` computes structural candidates and distinguishes no common type from no unique least type. Compatible nominal/function arguments are solved independently instead of enumerating every combination.

`variance.ts` checks declarations and conversions. Some built-in constructor variance is encoded explicitly, including `List` and `Map`.

Literal joining can mutate defaulted HIR literals in place. The `WeakSet` marking expressions is separate from the strong global set marking their spans.

## Speculation And Retry

### Candidate Transactions

[call-speculation.ts](../../src/checker/call-speculation.ts), `speculate`, takes a trial and restores state in `finally`. It preserves aliases and object identities and supports nested trials.

Ordinary objects use recursive descriptor/collection snapshots. Production checker objects participate through `TRIAL_STATE` and [checker-trial-state.ts](../../src/checker/checker-trial-state.ts).

Immutable declaration registries are skipped. Closures, globals, diagnostics, and range-pattern conditions receive shallow collection snapshots; other mutable state is traversed.

`LazySignatures` journals changed entries rather than walking its entire registry. `SignatureInference` journals pending/failed result state and snapshots its inference stack, globals, and diagnostics.

The selected candidate is checked again outside the transaction. Trial output serves selection; it is not committed HIR.

The earlier whole-state performance description is therefore outdated as a complete description. Current snapshots still incur costs proportional to participating state, but skip substantial immutable input.

### Literal Retry

[checker.ts](../../src/checker/checker.ts), `retryStatement`, uses a different rollback mechanism from candidate transactions. It retries a failing statement at widths named by its diagnostics and suppresses nested retries within a trial.

[literal-retry.ts](../../src/checker/literal-retry.ts), `markState` and `restoreState`, record array lengths and map sizes. Restoration truncates appended array entries and removes appended map entries.

This mechanism does not restore overwritten preexisting map values or arbitrary object-field mutations. Its safety therefore depends on retry paths obeying an append-only mutation contract.

The existence of the weaker contract is source-confirmed. This audit has not established an end-to-end retry corruption case.

### State Outside Transactions

Module-global derivation origins, map-key facts, and literal metadata are outside `CheckerContext`. A checker transaction does not automatically restore those objects.

The [findings report](findings-2026-10-04.md) demonstrates literal span retention across repeated compiles. It also documents source-key reuse in the derivation diagnostic helpers.

This matters to an in-process test worker, the REPL, browser workers, and any future long-running compiler service. A fresh command-line process can conceal lifecycle problems.

## Derivation And Std Integration

[standard-library.ts](../../src/checker/standard-library.ts) loads the reached std use graph, resolves exported names, and chooses visible or hidden declaration spellings. Parsed modules and renamed variants are cached.

Cached syntax does not mean cached checked std HIR. Std declarations participate in the semantic passes for each compilation.

[standard-provenance.ts](../../src/checker/standard-provenance.ts) rebuilds syntax objects with physical origins and logical joined-program anchors. Subsequent transforms must preserve that metadata.

[typed-derivation.ts](../../src/checker/typed-derivation.ts) is a substantial frontend within the checker. It manages facts, member models, templates, hidden protocols, tuple shapes, generated traversal code, and diagnostics.

[template-instances.ts](../../src/checker/template-instances.ts) compiles template methods into generic helper declarations and creates target implementations. Its "checked once" description is about template expansion within that preparation, not a persistent checked-stdlib cache.

[generated-source.ts](../../src/checker/generated-source.ts), `Source_.program`, parses synthesized hd source and patches placeholders back to user expressions/types. A grammar change can therefore affect both written programs and the compiler's own generation templates.

Placeholder handles use NUL and allocate names avoiding existing spellings. Line-specific spans restore user anchors after parsing generated text.

`@error` uses a separate preparation pass because it is an intrinsic independent of ordinary name resolution. Its generated code then enters ordinary checking.

## HIR Production And Diagnostics

[program-lower.ts](../../src/checker/program-lower.ts) constructs implementation records, checks the module body before ordinary declarations, performs inference, and gathers checked functions. It then validates initialization and converts captured mutable locals.

[captured-cells.ts](../../src/checker/captured-cells.ts) maps captured mutable, non-parameter locals to `cell:T`. Binding becomes cell allocation, assignment becomes cell mutation, and closure environments store the shared cell.

Its mapper keys by `HirLocal` identity and finds closures by explicit index. The typed walker preserves metadata and visits dictionary bounds and match tests.

The emitter still imports `cellInner` from this checker module. Capture-cell representation is thus a cross-stage internal contract.

`CheckerContext.fail` adds a diagnostic and throws `CheckFailure`. `check()` catches that sentinel at the function boundary and produces no function HIR.

The program can collect failures from several functions. Within a failing function, checking normally stops at the first fatal failure; literal retries can replace or refine that diagnostic.

Warnings are gathered through separate paths. Unused-local warnings rewalk the completed HIR to collect read local identities.

No HIR is returned when final diagnostics include errors. That gives the backend a useful success gate, but not an explicit independent HIR verifier.

## Evidence And Successor Questions

Focused tests passed for speculation, types, requirements, captures, std loading, reachability, and suspension integration. The full selected portable suite also passed.

The repeated-compilation probe used the unchanged `literal-first-use-fallback.hd` fixture. It reported no diagnostics while retaining 12 additional span objects per analysis.

The next architecture discussion needs explicit answers about the lifecycle of compilation facts, the representation of types, and where preparation ends and semantic checking begins. It also needs a stated rollback contract for each retry mechanism.

Those are questions about implementation boundaries. This audit makes no language change and selects no replacement compiler design.
