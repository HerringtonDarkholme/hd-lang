# Spec Coverage And Correctness Audit (2026-10-15)

hd commit `c784a0eb`, `target/debug/hd` (default features, Node engine).
Issue #169. The question: which spec rules have no test, and do the
untested ones work? Audit only. Nothing in the compiler, spec, or fixtures
changed.

Method:

- A throwaway script mapped every `r[id]` in `spec/lang`, `spec/std`, and
  `spec/cli` (5978 rules) to its nearest heading. It counted the cases that
  `cases.tsv` indexes to that heading (directly, or to a rule anchor
  inside it) and the `cli-cases.tsv` cases that cite one of its rule IDs.
  Seven `cases.tsv` rows cite a whole chapter with no anchor; they are not
  counted.
- From the zero-case and thin sections I picked the rules most likely to be
  wrong: typing rules with a code, run-time semantics, and CLI behaviour.
  I skipped message wording and error positions.
- Each pick got the smallest program that would show a violation, valid
  and invalid where the rule has a code, run with
  `HD_CACHE=target/cov/cache target/debug/hd FILE` or `hd check FILE`.
  Probes live in `target/cov/p/` and are not committed.

Not probed: REPL rules (the default build has no wasmtime engine, and the
REPL refuses to start without it), remote versions and `hd.sum` content
(they need a git host), and the Wasm host boundary (needs an embedder).
`--max-heap` is ignored on the Node engine with a warning. That is the
known W5 gap, so it is not counted here.

The core language and std are in good shape. Every probe of evaluation
order, overflow, shifts, casts, float display, optional nesting,
propagation and `From`, defer order, iterator invalidation, providers,
construction-time binding, `race!`/`all!` cancellation, derivations, JSON,
regex, integer parsing, and property-test edges matched the spec. The bugs
are at the edges: missing checks on rare invalid forms, panic reports, one
diagnostic's content, and unbuilt CLI commands.

## Bugs

Each group is sized for one issue of about an hour, except G7.

### G1. `Self` outside a trait or `impl` body is accepted

Severity: accepts an invalid program. Rule: `names.self-type.outside`.
Likely crate: `hd_resolve` (`lower.rs`, type-name lowering), then `hd_check`.

```hd
fn f() -> Self:
    "text"
fn g(x: Self) -> i32: 1
data P:
    s: Self
```

`hd check` prints `check result: ok`. Running a program that calls `f`
fails late with `unsupported: stage Emit: the layout of the non-concrete
type {poison}`. So the resolver makes a poison type and reports nothing.
Expected: an error at each `Self`. The spec names no code; `unknown-type`
fits.

### G2. `pub` is accepted on a local function

Severity: accepts an invalid program. Rules: `names.local.no-pub`,
`fn.local.private`. Likely crate: `hd_syntax` (`parser/items.rs`, where
the local-decorator check `decorator-not-top-level` already lives).

```hd
fn outer() -> i32:
    pub fn helper() -> i32: 1
    helper()
```

`hd check` prints `check result: ok`. Expected: an error. A local
`@derive` is already rejected, so the same position check can cover `pub`.
The spec names no code.

### G3. Duplicate string or float literal arms are not unreachable

Severity: accepts an invalid program. Rule: `flow.match.unreachable`
("duplicate unguarded literals ... are errors"). Likely crate: `hd_check`
(`pat.rs`).

```hd
fn f(s: string) -> i32:
    match s:
        "a" => 1
        "a" => 2   # expected unreachable-match-arm
        _ => 3
```

Accepted. The same holds for `1.5` twice on an `f64` subject, for
`("a", _)` then `("a", 2)`, and for `.A("x")` twice. `bool`, integer
(ranges too), and `char` duplicates are reported correctly. So the
reachability check only tracks value spaces it can enumerate.

### G4. `hd FILE` panic reports have no source location

Severity: wrong result at run time (the panic report). Rules:
`flow.panic.report`, `flow.panic.report.fallback`. Likely crate: `hd_cli`
(`main.rs:489` prints only category and message), fed by the host in
`host/core.mjs`.

```hd
pub fn main() -> void $ Console:
    count := 0
    println("${count - 1}")
```

Prints `panic: integer-overflow: integer overflow`, exit 3. Expected:

- a source location, which `flow.panic.report` requires "when one is
  available". `hd test` already prints symbolized frames for the same
  panic, so the location exists;
- for this program, a note that `count` fell back to `usize`, with a
  signed-literal or annotation suggestion (`flow.panic.report.fallback`).

`panic("boom")` and `xs[5]` report no location either.

### G5. The `folder-cycle` diagnostic lacks its required content

Severity: wrong diagnostic. Rules: `module.cycle.diagnostic.loop`,
`module.cycle.diagnostic.size`, `module.cycle.diagnostic.fix`. Likely
crate: `hd_driver` (`lib.rs` builds the folder graph).

Repro: a package with `src/shop/mod.hd` holding `use pkg.cart.items` and
`src/cart/mod.hd` holding `use pkg.shop.shop_name`. `hd run` prints:

```text
error: folder-cycle: folders form a cycle: cyc.cart -> cyc.shop
```

The detection is right. But the message has no file position, no `use`
declaration per edge, no closing node, no tangle size, and no fix-it.
Expected, per the spec example:

```text
folder-cycle: src/shop -> src/cart -> src/shop
tangle of 3 folders; move src/cart.hd to src/cart/mod.hd
```

### G6. Child-trait widening inside a list reports `type-mismatch`

Severity: wrong error code. Rules: `types.variance.repr.excluded`,
`types.variance.no-insertion`. Likely crate: `hd_check` (`body.rs`, where
`variance-representation-change` is chosen).

```hd
trait Animal:
    fn name(self) -> string
trait Dog < Animal:
    fn bark(self) -> string
fn f(items: List[dyn Dog]) -> List[dyn Animal]:
    items   # expected variance-representation-change
```

Reports `type-mismatch`. `List[i32]` to `List[dyn Display]`, `List[i32]`
to `List[i32?]`, and the contravariant function case all report
`variance-representation-change` correctly. Only the child-to-supertrait
step falls through.

### G7. `hd fix` is advertised but not routed

Severity: rejects a valid command. Rules: `cli.fix.command`,
`cli.fix.safe`, `cli.fix.overlap`, `cli.fix.rounds`, `cli.fix.report`,
`cli.fix.status`.
Likely crate: `hd_cli`.

`hd --help` lists `fix` and `hd help fix` describes it. But `hd fix` in a
package with an `old-row-separator` and a `missing-let`, both with
fix-its, prints the usage text and exits 101. This was already in
gap-audit-2026-10-10 Tier 3. What is new is that the help now advertises
it. Larger than an hour.

### G8. The compiled cache has no cap, and `hd cache gc` is not routed

Severity: rejects a valid command, and the cache grows without bound.
Rules: `cli.cache.gc`, `cli.cache.gc.anywhere`, `cli.cache.obj.cap`,
`cli.cache.obj.evict`. Likely crates: `hd_cli` and `hd_cache`.

- `hd cache gc` prints the usage text and exits 101, though `hd --help`
  lists it.
- No crate reads `HD_CACHE_MAX_SIZE`. `hd_cache/src/store.rs` has an
  eviction planner, but its own comment says "the store never evicts", and
  nothing calls it with the 10 GiB default cap. Running with
  `HD_CACHE_MAX_SIZE=1M` leaves a 21 MB `obj` directory untouched.

## Spec Unclear

1. `types.literal.local.signed`: in `-2 ** 2` with no expected type,
   `-` applies to `2 ** 2`. Is `2` "written directly after unary `-`",
   and so a signed literal? The implementation says no: `2 ** 2` is
   `usize`, and `-` on it is `type-mismatch`. With `let y: i32 = -2 ** 2`
   it gives -4.
2. `flow.match.cover.enum` requires "every inhabitable variant", but no
   rule defines inhabitable. The implementation requires an `.Err` arm on
   `Result[i32, never]`.
3. `module.dbg.line`: `dbg()` with no arguments prints a bare
   `FILE:LINE:COL` line. The rules give one line per argument, so zero
   lines.
4. The `module.dbg.value` example `fn audit(account: Account) -> Account:
   dbg(account)` cannot check, since `module.dbg.signature` makes `dbg`
   return `void`.
