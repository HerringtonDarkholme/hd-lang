## R1. Optional Collision Survives Through HIR And Wasm Representation

[The parser](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/parser.ts#L1039) drops grouping for non-tuple parenthesized types. [Optional construction](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/types.ts#L229) appends `?`, preserving extra grouping only for function types. [Mutable construction](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/parser.ts#L1070) prepends `mut:`.

This independently derives the same encoded type, `mut:User?`, for a payload-mutable optional and an outer-mutable optional. The explicit spelling `Option[mut User]` is not a workaround: [the generic type parser](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/parser.ts#L1149) immediately converts it through the same `optionalType` helper.

The distinction matters under `types.option.invariant`, `types.option.propagate.permission`, and `types.assign.weaken`. The existing [option-invariant fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/option-invariant.hd) documents the payload weakening that must fail. Its known-failure status was read rather than revalidated.

[Checker coercion](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L453) recognizes leading permission weakening and constructs `permission-weaken`. [Assignability](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L83) recursively strips the prefix. The compiler has already lost evidence that this permission belonged inside an invariant constructor.

[Wasm type selection](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/context.ts#L236) strips leading mutable permission before selecting the optional carrier, and [optional/result recognition](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/types.ts#L252) uses `$hd.variant`. [Noncallable weakening emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/function-body.ts#L445) simply emits the operand. Both intended type structures can legitimately share a physical carrier; this physical equality cannot authorize their semantic conversion.

Correction to any stronger backend diagnosis: T1 does not require a malformed Wasm layout. It can generate valid Wasm for an incorrectly accepted semantic conversion. Wasm validation cannot detect optional invariance after the checker erases the distinction.

Migration dependency: preserve constructor nesting and permission placement in parsed types before changing assignability. Updating the emitter or `optionalInner` alone cannot reconstruct the missing parse information. Parsing, substitution, propagation, alias expansion, generic matching, and diagnostics must all agree on the new structure.

## R2. T4 Is A Semantic Relation Gap, With More Than One Join Site

[Least-common-type candidates](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L143) enumerate outer weakening and readonly List covariance. [The joining relation](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L163) receives no nominal declarations. [Variance conversion](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/variance.ts#L130) receives declarations but evaluates changed arguments through `isPermissionWeakening`, which itself lacks custom declaration variance.

The resulting asymmetry is confirmed: expected-type coercion consults a declaration-aware outer variance check, while inference and nested argument conversion consult narrower relations. For readonly `Producer[mut User]` and `Producer[User]`, candidate enumeration gives disjoint singleton sets. The emitted runtime shape is not the reason for that restriction.

[Nominal Wasm selection](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/context.ts#L269) maps generic data/enum instantiations to the declaration's one `$d`/`$e` index. [Nominal field layout emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/emitter.ts#L1329) follows declaration fields, and generic storage uses [erasure/restoration](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/context.ts#L470). Permission changes can therefore preserve that representation. This supports the report's checker diagnosis; it does not prove every possible nested generic conversion is runtime-safe.

Additional correction: [uncontextualized if expressions](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-control.ts#L94) compare branch types for equality or `never`, then try only function row union. They do not call `leastCommonType`. Expanding that helper's candidates therefore cannot fix every specified join site. [Inferred return accumulation](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L1189) likewise uses equality/`never` plus row union, providing another join site for the next traceability pass.

Rules `types.lct.conversions` and `types.lct.no-combine` both remain relevant. A unified relation must retain the explicit prohibition on combining outer permission weakening with a variance step for one inferred candidate. Recursively removing every `mut:` is not a valid substitute for that rule.

### Callable Representation Qualification

[Signature collection](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/module-types.ts#L30) canonicalizes the outer permissions of direct callable parameters and results. `SignatureMap` applies this key on get, has, and set. Thus a direct function permission conversion need not select a distinct closure struct. Any blanket claim that every distinct function type string yields a distinct runtime signature would be wrong.

The key does not recursively canonicalize permissions inside arbitrary generic arguments. That leaves layout-equivalent nested function forms dependent on the adaptation machinery. The extent of correct nested canonicalization remains unvalidated.

[Permission weakening emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/function-body.ts#L445) nevertheless calls `adaptCallable` for callable operands. [The adapter](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/context.ts#L453) allocates a closure wrapper even when signature IDs coincide. That allocation is confirmed source behavior; its conformance classification needs care.

`types.variance.no-insertion` forbids metadata rewrapping, copies, and per-access conversions; `fn.type.variance-repr` requires permission-only representation-preserving conversion. Row subsumption and generic erasure adapters have distinct reasons to exist. The later audit must distinguish unavoidable ABI adaptation for those mechanisms from an unnecessary wrapper for pure permission variance. This pass does not promote wrapper allocation alone to a reproduced semantic failure.

Migration dependency: define semantic assignability, permitted inferred candidates, and representation compatibility as explicit related operations. They must share declaration identities without pretending they are the same relation. Maintain a distinct runtime signature key so semantic TypeIds do not accidentally force redundant Wasm types or wrappers.

## R3. Two Std Aliases Reveal Binding Identity Loss, Not A Syntax Restriction

[Import validation](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-validation.ts#L27) records local-name-to-origin bindings and rejects duplicate local names. It does not reject two distinct aliases of one declaration. The use grammar allows aliases, and `module.use.whole-module` requires resolving these bindings before type checking.

[Standard local-name selection](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L491) writes one local name per qualified declaration into a map. A later alias overwrites an earlier alias. [Std joining](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L682) physically renames one copy of the declaration to the selected local spelling.

[Function lookup](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L1429) reads signatures using the requested local spelling. [Declared calls](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-calls.ts#L1154) do not redirect that lookup through the import-origin map. Consequently, preserving two valid import AST entries does not preserve two usable names for one function. This is semantic binding identity loss even if the regex rename were token-perfect.

The existing [single-alias test](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/test/std.test.ts#L121) demonstrates an accepted ordinary alias and absence of the original unimported spelling. It does not exercise two aliases of one origin. The predicted missing-alias diagnostic remains unexecuted.

[Regex source renaming](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L257) has additional token, string-literal, scope, and syntax hazards described by SOURCE-4. Those should remain separate evidence categories. Replacing regex substitution with a token-aware substitution would address some hazards but retain the one-origin-to-one-local-name restriction. Parsing source once likewise cannot rescue missing binding identity by itself.

Migration dependency: keep canonical declarations independent of import bindings. Name resolution must turn each alias into the same declaration ID before emission. Lang-item recognition, typed derivation's `standardOrigin`/`programNames`, hidden std names, source spans, and tests that assume renamed declarations all depend on this change. These dependencies argue for staged adapters and explicit verification, not a superficial renaming patch.

## R4. Nested Return Candidate Survives The Existing Checking And Rewriting Stages

Challenge question: does the checker already rewrite nested return into suspension completion, or force CFG for this source shape?

[Statement checking](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/statements.ts#L246) validates the language return type and returns a HIR statement with `kind: "return"`. [Conditional checking](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-control.ts#L75) preserves checked branch suites in the HIR `if`. [Function checking](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L323) stores that body directly; [fallthrough validation](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L1203) only checks types and does not transform exits.

[The final program rewrite](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-lower.ts#L214) is capture-cell conversion. [Its return-preserving generic traversal](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/captured-cells.ts#L82) rewrites children but supplies no poll-aware return conversion. A function with no shared mutable capture bypasses that rewrite entirely.

[CFG selection](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/suspension.ts#L138) tests nested drive placement, not nested return placement. A separate branch without a drive stays on the linear path when another top-level binding supplies a direct drive. [Linear continuation emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/emitter.ts#L1024) intercepts only top-level returns.

[Ordinary if emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/function-body.ts#L904) emits branch blocks through [ordinary statement returns](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/function-body.ts#L128). That becomes a native return from [the linear poll function](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/emitter.ts#L853), whose protocol result is `i32`. No reviewed pass changes the target to [suspension completion](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/emitter.ts#L1109).

The prior prediction therefore remains: an i32 early return can bypass stored result/completion/outer cleanup; a non-i32 or bare void return can produce an invalid poll body. Separate non-driving postfix propagation follows [ordinary native return emission](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/emitter/function-body.ts#L315). Neither prediction is an executed result.

The smallest existing seed remains [sequential-suspending-calls.hd](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/runtime/valid/sequential-suspending-calls.hd). Keep one direct drive and vary only a separate branch's exit. Avoid nesting the drive inside that branch: that would select CFG and test a different path. Helpers can supply non-entry result types, avoiding entry termination constraints.

## Remaining Coverage And Migration Risks

Read fully: both challenged reports. Independently inspected the relevant parser type constructors; type permission/optional helpers; assignability candidates and comparisons; nominal variance conversion; checker coercion, branch joins, return accumulation, return statement construction, and function body assembly; std alias selection/import lookup; emitter type selection, signature canonicalization, erasure, callable adaptation, and linear completion paths.

Outstanding: complete alias expansion and generic normalization, every inference join site, declaration variance validation after inherent methods, nested function layout canonicalization, callable identity observability, complete template hygiene, capability/lang-item recognition under canonical import IDs, and runtime reproduction of each predicted failure. No claim of full file or compiler coverage is made by this challenge pass.

The dependency order supported by this evidence is: retain semantic type structure and declaration ownership; resolve aliases/scopes to identities; consolidate semantic conversion relations while preserving their inference restrictions; define representation compatibility; and consolidate control-flow lowering. A shared IR transition must preserve capture-storage IDs, origin spans, generic erased ABI plans, requirement rows, and poll completion semantics. Changing any one representation without auditing its consumers can replace a known limitation with a new silent miscompile.
