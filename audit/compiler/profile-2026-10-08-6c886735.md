## Scope And Method

Same harness and method as the previous report:
`bench/profile-signature` at 200 and 2,000 functions per folder (3,009
and 30,009 generated lines, plus embedded std), median of five
processes; signature edits in fresh processes; `hd run` / `hd build` on
the samples through Node/V8 (five runs after one warm-up, seven for
`hd build`). Two changes since last time, both outside the measured
code: the driver's bench generator now emits reassignable `let`,
`shape_*` names and a `$ Console` entry (P2 follow-ups `55bae2b4`,
`8393d07f`), so this run updates only the harness's signature-edit
anchors (`shape_0`); and `hd run DIR` is now rejected, so samples run
through the spec forms (bare `FILE.hd`, or in-package `hd run`).

Samply still fails on this host and macOS exposes no counters, so
native symbols, allocations and peak RSS remain **no data**. Rankings
use the driver's stage timers. Load stayed under 13 for the harness
runs.

## Findings

- Nothing to flag: every stage and every sample is within noise of the
  previous report, and the pool still helps every path (0.52–0.90×).
  The measurable changes since last time are all repairs, not
  regressions: benches compile again, `hd run DIR` fails fast with a
  usage error, header diagnostics carry positions.
- The untimed remainder (scheduler/graph/cache/driver, 56.35 ms cold)
  stays the largest single row with no function-level owner; sampled
  symbols would still be the way to split it.
- Bench maintenance is now shared: the generator fixes landed in
  `hd_driver/src/bench.rs` itself, and the profile harness keeps only
  the signature-edit anchors plus drift guards that are currently
  no-ops.
