## SOURCE-1: metadata is preserved, semantic ownership is lost

The linker retains a `PackageModule` with path, module identity, and parsed program ([package.ts:42](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L42)). It also creates `LinkSegment` metadata for mapping diagnostics to original files ([package.ts:49](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L49)). The result returns both `modules` and `locate` alongside concatenated source ([package.ts:516](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L516)). Therefore “all module identity disappears” would be an overstatement.

The material finding survives this counterevidence. The joined source removes package uses and leaves declarations in one namespace ([package.ts:528](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L528)). Duplicate spellings across modules are explicitly rejected before joining ([package.ts:416](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L416)). The file header acknowledges that direct private references and integration-test access are not isolated ([package.ts:14](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L14)). Source segments can locate an error but do not attach original module ownership to each resolved declaration or constrain lookup.

The linker does enforce publicity for explicit imports through `exporter` ([package.ts:242](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/package.ts#L242)). This is meaningful partial implementation. The report should avoid claiming it performs no visibility checks; the weakness is the path that names declarations directly after flattening.

The cited requirements remain applicable: `module.vis.private-default`, `module.vis.no-package-private`, `module.testing.it.unique`, and `module.test.integration.view`. Whole-module ordering also lacks the statement scheduler demanded by `module.init.group.step`. Those conclusions remain source-derived, with executable failure records still unverified in this pass.

## SOURCE-2: the shadowing counterarguments do not prevent the rewrite

The best possible defenses would be a reserved receiver spelling, a prelude shadowing prohibition, or ordinary checker local resolution running before the transformation. None protects the described case.

`with` is absent from the lexer keyword set ([lexer.ts:61](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/lexer.ts#L61)), and `arbitrary` is absent from the fixed public prelude imports ([prelude.hd:13](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/lib/std/prelude.hd#L13)). `std.testing.arbitrary` really declares an ordinary function named `with` ([arbitrary.hd:18](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/lib/std/testing/arbitrary.hd#L18)). Inner-scope shadowing is permitted by `names.scope.shadow` ([03-names-and-scopes.md:84](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/03-names-and-scopes.md#L84)).

`withStandardSubmodules` recursively visits every AST object, recognizes a matching member receiver by spelling, and substitutes a hidden named callee ([standard-library.ts:607](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L607)). The checker pipeline calls this before ordinary expression checking ([program.ts:67](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program.ts#L67)). Later expression checking normally does respect locals and captures ([expression-calls.ts:119](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-calls.ts#L119)), but that lookup sees the newly generated callee, not the removed local receiver.

Scope qualification: this is not every std member access. The branch requires `result.kind === "call"`, a member callee, a simple name receiver, and a function declared by that std module. A suspending call, complex receiver, or unmatched member spelling does not follow this branch. The ordinary `arbitrary.with` example meets the branch conditions. Its final acceptance, rejection, or wrong result needs a compiler probe before the consolidated audit calls it a reproduced defect.

## SOURCE-3: protected literal values do not protect member identities

One potential defense is `patch` skipping string properties named `value` ([generated-source.ts:69](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/generated-source.ts#L69)). That protects literal payload strings, not a member expression's `name`, a constructor field label's `name`, or a variant spelling. It does not weaken the reported member collision.

The target type is the first placeholder issued by the generation function ([typed-derivation.ts:1028](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/typed-derivation.ts#L1028)). Consequently `HDTYPE0X` has a defined replacement there. Data getters interpolate `member.access` directly after `s.` ([typed-derivation.ts:1123](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/typed-derivation.ts#L1123)). Constructors similarly interpolate field labels and enum variants ([typed-derivation.ts:1257](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/typed-derivation.ts#L1257)). The parsed generated AST is then patched indiscriminately across non-`value` strings ([generated-source.ts:67](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/generated-source.ts#L67)).

No lexical rule reserves `HDTYPE0X`; the identifier rules permit its ASCII spelling ([01-lexical-structure.md:359](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/01-lexical-structure.md#L359)). There is also no token-boundary protection in the placeholder regular expression. The report's core corruption mechanism is confirmed from source. A final diagnostic cannot be named reliably without running the complete derivation/checker pipeline.

Original expression placeholders are returned as original AST nodes at [generated-source.ts:75](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/generated-source.ts#L75), rather than recursively patched afterward. Thus arbitrary user expressions embedded through `out.expression` are not all vulnerable in the same way. Keep the finding specifically about user spellings copied into generated source. The separate `hdexprN` collision lead remains unresolved.

## SOURCE-4: the cmp.min alias case has no fallback

`standardLocalNames` stores one local spelling per qualified declaration, so repeated imports overwrite that value ([standard-library.ts:491](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L491)). The later prelude export loop can override names for prelude declarations, making “the last alias always wins for every std item” too broad. However, `min` is not a prelude export ([prelude.hd:15](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/lib/std/prelude.hd#L15)), so the original example isolates the overwrite cleanly.

The validator accepts distinct local aliases and records both qualified origins ([program-validation.ts:27](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-validation.ts#L27)). `names.use.no-collision` forbids duplicate local bindings, not two distinct bindings pointing to one declaration ([03-names-and-scopes.md:198](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/03-names-and-scopes.md#L198)). No reviewed rule forbids the original example.

Ordinary `checkDeclaredCall` looks up the local callee spelling ([expression-calls.ts:1154](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-calls.ts#L1154)); `visibleSignature` follows neither recorded import origin nor an alias map ([context.ts:1429](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L1429)). A few compiler-known calls do follow `imports` for their own intrinsic behavior, so this should not be generalized to all std names. `cmp.min` follows the ordinary signature path.

The existing one-alias test proves its intent is local alias binding and leaves the original spelling unavailable ([std.test.ts:121](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/test/std.test.ts#L121)). It does not cover two simultaneous aliases. The missing signature for the earlier alias is a well-supported prediction, with final compiler evidence still outstanding.

The report correctly limits regex literal corruption and Unicode-boundary claims to architectural risks. `renameSource` demonstrably ignores token structure ([standard-library.ts:249](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/standard-library.ts#L249)), but this challenge found no actual current std string corruption. Preserve that qualification.

## SOURCE-5: the spec cannot presently serve as one consistent oracle

`grammar.tests.statements` unconditionally restricts each statement to a prelude `it` call ([02-grammar.md:71](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/02-grammar.md#L71)). `module.testing.position-statements` explicitly allows other registration functions ([10-modules.md:872](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/10-modules.md#L872)), and `std-testing.registration` names those functions ([testing.md:47](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/std/testing.md#L47)). These are conflicting normative requirements, not merely different explanatory examples.

`finishTestCases` recognizes imports of `it_each`, `it_prop`, and `it_prop_with` and handles their calls ([test-cases.ts:393](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/test-cases.ts#L393)). The linked [derived-arbitrary-with fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/runtime/valid/derived-arbitrary-with.hd) indeed uses `it_prop` directly. Agreement between those two artifacts supports one interpretation but cannot amend the narrower normative grammar.

The tier claim also withstands review. AGENTS.md places compiler-checked test-position rules in the language tier. The stdlib registration rules determine permitted compiler positions and require literal-name errors; the numbered language rule directly delegates its accepted function set to stdlib. This does not pass the stated ordinary-hd implementation test. Existing generic diagnostic codes do not eliminate the tier problem, because the compiler must know which items receive those restrictions.

The original proposed owner question is correctly a question, not an implementation instruction. Historical decision review is still necessary before settling the intended behavior or moving rules. No current code acceptance should be labeled a compiler conformance failure solely against this contradictory grammar rule.
