# Types, inference, and checker architecture: first pass

Baseline: `823f346878028aad4a4c9351593217f04445bd4c`. This report reviews existing source and fixtures in the isolated audit worktree. No compiler, specification, or fixture was changed; no checks or new hd programs were run. Static deductions below are distinguished from execution results.

The sections under review are [local declarations](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/03-names-and-scopes.md#local-type-declarations), [local implementations](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/03-names-and-scopes.md#local-implementations), [optional identity and variance](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/04-type-system.md#optional-identity-and-variance), [variance](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/04-type-system.md#variance), [least common type](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/04-type-system.md#least-common-type), [function declarations](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/07-functions.md#declarations), [method resolution](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/09-traits.md#method-resolution), and [omitted requirement clauses](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/lang/11-requirements-and-suspension.md#omitted-requirement-clauses). Known issue labels identify earlier evidence, not independent confirmation of behavior. Owner decision history has not yet been reconstructed for every section.

## Architectural model found

Types enter the AST as `TypeRef { name: string, span }` ([ast.ts:11](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/ast.ts#L11)). HIR retains `ValueType = string` ([hir.ts:3](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/hir.ts#L3)). `types.ts` decodes this private type language using prefix tests, regular expressions, delimiter scanning, and recursive string reconstruction.

Program checking performs several source/AST transformations before constructing type environments. It injects standard declarations, hoists local declarations, applies defaults, and expands aliases before type declaration and implementation preparation ([program.ts:122](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program.ts#L122)). Function checking combines inference, coercion, provider resolution, captures, diagnostic production, and HIR construction through an inheritance chain. Shared mutable state includes locals, scopes, captures, inferred rows, inferred returns, pending call generics, and provider scopes ([context.ts:193](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L193)).

These choices can support a simple compiler, but they make preserving type structure and speculative checking difficult. The strongest findings below are cases where the representation or phase boundaries already restrict the general rule.

### T1. The type encoding loses optional permission placement

Parenthesized non-tuple types discard their parentheses before optional suffix construction ([parser.ts:1039](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/parser.ts#L1039)). `optionalType` preserves grouping only for function types ([types.ts:228](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/types.ts#L228)). A `mut` prefix simply prepends `mut:` to its recursively parsed inner type ([parser.ts:1050](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/parser/parser.ts#L1050)).

Consequently, `(mut User)?` becomes `mut:User?`. An outer mutable optional, `mut User?`, becomes the same string. `isPermissionWeakening` then removes the leading `mut:` and can treat this as `User?` ([assignability.ts:82](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L82)). This is loss of semantic information at parsing, so a more careful backend cannot recover the distinction.

The spec gives `T?` exact `Option[T]` meaning (`types.option.sugar`) and makes its payload invariant (`types.option.invariant`). Permission weakening changes an outer view (`types.assign.weaken`), while unwrapping must preserve the declared payload permission (`types.option.propagate.permission`). Those rules distinguish the two structures coherently. The existing [option-invariant fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/option-invariant.hd) explicitly expects rejection of the payload weakening. [KNOWN_FAILURES.tsv:71](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/test/portable/KNOWN_FAILURES.tsv#L71) records acceptance under VARIANCE-UNWRAP.

The source trace independently explains that record; execution has not been repeated. Further probes should cover nested Option/Result, aliases, stored fields, propagation, and `Option[mut User]` versus parenthesized sugar. Any eventual representation must retain constructor nesting and outer permissions as separate structure.

### T2. Trait selection refuses arguments the checker cannot safely retry

When several candidates belong to one generic trait, dot-call selection checks `speculationSafeArguments`. If it fails, the checker immediately reports `ambiguous-method` with the message that multiple traits supply the method ([expression-calls.ts:757](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-calls.ts#L757)). The blacklist includes closures, `if`, `match`, loops, comprehensions, bindings, provider constructs, pipes, and suspension calls ([call-speculation.ts:7](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/call-speculation.ts#L7)). It recursively searches the entire argument tree.

This prevents selecting a unique candidate even when such an argument has an unambiguous type. Replacing an argument with an equivalent `if` expression therefore changes whether overload selection can proceed. The diagnostic can also falsely describe one trait as multiple traits.

The spec's `trait.resolve.fits`, `trait.resolve.fits.expected`, and `trait.resolve.one-fit` define selection by argument and expected-result typing. They impose no syntax blacklist. Existing [argument-selection coverage](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/runtime/valid/generic-trait-instantiation-by-argument.hd) uses literals, data construction, and no-argument result selection; it does not reach these excluded expression forms. The associated negative fixtures test real ambiguity and no fit, rather than a unique fit containing a control expression.

Candidate trials restore only diagnostic length ([expression-calls.ts:770](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/expression-calls.ts#L770)). Other checker state is mutable, so removing the blacklist alone would require a separate correctness argument. The unresolved architectural question is how candidate checking becomes independent: explicit inference constraints, an isolated checker state, or a complete state transaction. The intended selection behavior is already specified; the implementation mechanism remains open.

### T3. Variance verification runs before the method surface exists

`varianceDiagnostics` takes only data and enum declarations and traverses fields, shared fields, and variant payloads ([variance.ts:86](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/variance.ts#L86)). It receives neither inherent method signatures nor their declarations. The call runs before `defineProgramTraits` and `prepareImplementations` ([program.ts:167](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program.ts#L167)). No other `invalid-variance` validator for inherent signatures was found in the reviewed checker files.

`types.variance.verified` and `types.variance.surface` require verification against the readonly public surface, including inherent methods. A parameter can therefore be positive in every stored field but negative in an inherent method parameter; the existing field-only analysis has no input from which to reject it. This is a missing global validation obligation, rather than a complicated emitter problem.

The [variance-position fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/variance-position.hd) puts the negative occurrence inside a function-valued field. It exercises a form the current walker handles. [variance-permission-weakening](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/valid/variance-permission-weakening.hd) demonstrates valid Producer/Consumer variance but has no inherent method surface.

There is a related explicit GADT obligation (`types.variance.gadt`). The HIR enum variant representation lacks the explicit result needed by that check ([hir.ts:37](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/hir.ts#L37)); enum definition keeps fields but not the source variant result ([program-types.ts:315](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-types.ts#L315)). The [covariant GADT fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/covariant-gadt-result.hd) is already listed as an unsupported GADT path with a different diagnostic ([KNOWN_FAILURES.tsv:4](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/test/portable/KNOWN_FAILURES.tsv#L4)). That gap should be tracked as unsupported syntax/semantics until the result structure is available, separately from accepting ordinary unsafe variance declarations.

The spec itself needs one clarification: “readonly public surface” and “every inherent method available with the nominal type” should define whether private methods contribute and from which visibility context. This does not justify omitting all inherent methods. Owner history and visibility rules must resolve that boundary before a fix is specified.

### T4. Assignability and inference have different, incomplete variance models

`leastTypeCandidates` knows outer permission weakening and covariance for the spelling `List`; all other types return only themselves ([assignability.ts:143](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L143)). `leastCommonType` intersects those candidate sets and uses `isPermissionWeakening` as its comparison relation ([assignability.ts:163](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/assignability.ts#L163)). Neither receives declaration variance information.

By contrast, ordinary coercion separately invokes `varianceConversion` with declared data/enum variance ([context.ts:456](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L456)). Thus a readonly `Producer[mut User]` can convert to `Producer[User]` in an expected-type context, while their inferred join has disjoint singleton candidate sets. Readonly Map value variance has the same enumeration gap even though `isPermissionWeakening` knows Map. Function variance also lacks candidate enumeration.

`types.lct.conversions` permits declared readonly variance. Existing [variance-permission-weakening](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/valid/variance-permission-weakening.hd) checks explicit expected types. [least-type-weakening-variance](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/least-type-weakening-variance.hd) checks the forbidden combination of outer weakening and a List variance step. Neither establishes that the inferred join works for user-declared covariance, Map values, contravariance, or functions.

The relation also fails to recurse through user-declared variance: `varianceConversion` tests argument conversions only using `isPermissionWeakening` ([variance.ts:152](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/variance.ts#L152)). That helper knows List, Map, and function types but has no access to custom declarations. Nesting a custom covariant Producer inside another covariant type therefore reaches a different rule set from nesting List.

Candidate composition probes should take existing Producer/Consumer values, join them in a list or inferred branch, and repeat with an equivalent built-in container. The expected no-combination restriction must remain explicit. The spec's broad `types.lct.unique` phrase also leaves the candidate treatment of optional injection less explicit than its treatment of trait erasure; owner history should resolve that detail independently of the clear variance gap.

### T5. Hoisting local implementations removes their lookup extent

Local declarations receive fresh synthetic names, and references are rewritten from their declaration point onward. That is a legitimate simple approach to preserving one static identity per local nominal declaration. However, a local `impl` is added to a program-wide array and removed from its executable suite ([local-declarations.ts:137](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/local-declarations.ts#L137)). The returned program merges these with all module implementations ([local-declarations.ts:174](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/local-declarations.ts#L174)). There is no retained suite identity, declaration-point visibility interval, or implementation-environment snapshot on affected call nodes.

Later checker contexts receive the full implementations and inherent-method arrays ([context.ts:193](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/context.ts#L193)). An earlier call on an already-visible local type consequently cannot distinguish an implementation introduced later in that suite. An implementation inside a child suite similarly retains no boundary that prevents lookup after the child suite ends.

`names.local-impl.extent` and `trait.impl.local.lookup` expressly restrict availability to the declaration point, enclosing suite, and child scopes. The existing [local-types fixture](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/valid/local-types.hd) places every call after the implementations. [local-impl-nonlocal-pair](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/spec/conformance/typing/invalid/local-impl-nonlocal-pair.hd) tests target eligibility, not extent. These fixtures can pass while this information is lost.

Candidate probes should move existing calls before a local implementation, and move the implementation into a child suite while retaining calls afterward. The evidence is a missing representation of lookup extent; the predicted acceptance requires execution confirmation. Global uniqueness checks remain necessary under `trait.impl.local.no-second`; preserving lookup extent must not accidentally create separate coherent implementations for one pair.

## Simple mechanisms that should not be condemned merely for being naive

Signature inference uses lazy result resolution with an explicit recursion stack and updates omitted requirement rows until no set grows ([program-inference.ts:79](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-inference.ts#L79), [program-inference.ts:141](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/program-inference.ts#L141)). These are reasonable simple mechanisms for `fn.decl.omitted-cycle` and `req.row.omitted.cycle`. Rechecking is a performance concern unless it demonstrably changes semantics or loses diagnostics.

The fixed bound depth of 64 is specification behavior (`trait.bound.depth.limit`), so `MAX_BOUND_DEPTH = 64` is not an arbitrary compiler hack ([shared.ts:1390](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/shared.ts#L1390)). Explicit standard lang-item handling, erased generic dictionary passing, and source spans on HIR likewise require case-by-case evaluation against the spec. Their presence alone is not a defect.

## Remaining risks and coverage

Expression checking dispatches through a sequence of optional handlers and finally throws an internal JavaScript error ([checker.ts:27](https://github.com/HerringtonDarkholme/hd-lang/blob/823f346878028aad4a4c9351593217f04445bd4c/src/checker/checker.ts#L27)). This confirms the maintenance risk recorded as F-610: the TypeScript discriminated union does not prove each kind has an owner. No currently reachable omitted kind was established here.

Generic identities are source-name strings such as `generic:T`, and the checker tracks pending generic names in sets. Alpha-renaming across nested generic callers, callees, methods, and closures is a valuable remaining probe. A caller/callee binder collision was not established by this review. Module nominal identity and package renaming require the package audit; bare-name maps alone do not prove linked modules collide.

Manual review covered `types.ts`, the HIR type/declaration interfaces, assignability and variance implementations, program inference, local declaration hoisting, and selected checker state, generic substitution, argument checking, and trait candidate selection paths. It did not cover every checker branch, trait coherence proof, GADT rule, associated binding normalization, provider entailment, module linker path, generic runtime layout, or diagnostic recovery path. Existing tests and known-failure records were read, not executed. No full conformance or owner-decision traceability claim is made.
