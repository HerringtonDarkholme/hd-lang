# Feature Fit

This document maps language features to the two main usage scenarios:

1. Interactive scripts and tool calls inside AI agents.
2. Engineering and infrastructure code generated by AI and reviewed by humans.

## Data Types, Schemas, And Validation

### Agent Tooling Fit

Typed data definitions should replace loose JSON inputs for tool calls.

They should support:

1. Tool input and output validation.
2. Sanity checks before a tool is executed.
3. Shared data types imported across files.
4. Generated external specs for existing ecosystems, such as JSON Schema, OpenAPI, MCP tool definitions, and TypeScript types.
5. Lightweight validation annotations for simple tool input/output constraints.
6. External `annotate Validation for ...` blocks for richer validation behavior.

### Engineering/Infra Fit

Typed data definitions should make generated code reviewable and testable.

They should support:

1. Field-level validation.
2. Zod-like validator composition.
3. Custom validators written as normal functions.
4. Property-test data generation.
5. Declarative lifecycle rules such as retention and cascade deletion.
6. Observability metadata that links runtime values back to source-level types.

### Tooling Needs

1. Schema/type checker.
2. Validator generator.
3. External spec generator.
4. Test data generator.
5. Serializer/deserializer generator.
6. Documentation generator.
7. Data lifecycle checker.

### Decisions

1. Schema should not be a separate declaration system.
2. Validation should not create distinct static subtypes by default.
3. Custom validators should be normal functions.
4. Invalid test data generation is not needed initially.
5. Minimal validation can be inlined through annotations.
6. Richer validation can be attached through general `annotate <Facet> for <Target>` blocks.
7. The same annotation mechanism should support other facets, such as database schema and UI rendering.

## Effects And Handlers

### Agent Tooling Fit

Effects should make tool dependencies and capabilities visible.

They should support:

1. Tool dependencies such as database access, network access, clock access, filesystem access, and auth.
2. Mock handlers for interactive agent testing.
3. Capability checks before tool execution.
4. Generated documentation of what a tool may do.
5. Sandboxed execution by default.
6. Interactive resumption for long-running or interrupted agent scripts.

### Engineering/Infra Fit

Effects should make AI-generated code easier to audit.

They should support:

1. Compiler-verifiable dependency usage.
2. Compiler-verifiable unhandled errors or required handlers.
3. Dependency injection through handlers.
4. Durable workflow steps as standard-library effects.
5. Observability as effects or effect-backed runtime capabilities.
6. Capability-aware runtime boundaries.
7. Effect-polymorphic higher-order functions that can propagate callback effects and remove internally handled effects.

### Tooling Needs

1. Effect checker.
2. Handler checker.
3. Mock handler generator.
4. Capability/audit report.
5. Effect graph visualization.
6. Sandbox runner.
7. Capability checker.
8. Effect-polymorphism checker, including effect-variable removal such as `e - log`.

## Contracts

### Agent Tooling Fit

Contracts should describe tool preconditions and postconditions.

They should support:

1. Rejecting invalid tool inputs before execution.
2. Checking tool outputs after execution.
3. Generating better tool documentation.
4. Producing structured diagnostics for AI repair.

### Engineering/Infra Fit

Contracts should make generated functions reviewable.

They should support:

1. Caller obligations through `require`.
2. Callee obligations through `ensure`.
3. Typechecked but not compile-time-proven predicates.
4. Test/debug checks by default, configurable for production.
5. Distinct effects for failed `require` and failed `ensure`.

### Tooling Needs

1. Contract typechecker.
2. Runtime checker.
3. Structured contract diagnostics.
4. Contract-driven test generation.
5. Documentation generator.

## Property Tests And Generated Data

### Agent Tooling Fit

Property tests should verify tool behavior over generated inputs.

They should support:

1. Auto-generated valid tool inputs from schemas.
2. Optional invalid input generation for negative tests.
3. Tool example checks.
4. Mocked dependency handlers.

### Engineering/Infra Fit

Property tests should increase confidence in AI-generated code.

They should support:

1. Schema-driven test data.
2. Contract-driven property checks.
3. Reproducible failures.
4. Shrinking failing cases.
5. Structured reports that AI agents can use to repair code.

### Tooling Needs

1. Property-test runner.
2. Data generator.
3. Shrinker.
4. Mock/effect handler integration.
5. Machine-readable failure reports.

## Tool Declarations And Registration

### Agent Tooling Fit

Tools should be normal functions registered through annotations.

They should support:

1. Tool descriptions.
2. Input/output types.
3. Error behavior.
4. Context/auth/access metadata.
5. Examples.
6. Cross-tool references.
7. Generated specs for external tool ecosystems.

### Engineering/Infra Fit

Tool registration should also support service endpoints, jobs, workflows, and operational entry points.

They should support:

1. Code-derived resource registration.
2. Observability setup.
3. Access-control wiring.
4. Deployment/sync metadata.

### Tooling Needs

1. Registration scanner.
2. Tool graph generator.
3. Spec generator.
4. Access-control checker.
5. Runtime registry.

## Observability

### Agent Tooling Fit

Observability should let AI agents inspect tool behavior without raw production data access.

It should support:

1. Logs.
2. Traces.
3. Metrics.
4. Structured diagnostics.
5. Links from runtime behavior to source-level declarations.

### Engineering/Infra Fit

Observability should make generated systems operable.

It should support:

1. Built-in logging/tracing/metrics primitives.
2. Operation context.
3. Workflow history.
4. Contract/test/runtime failure correlation.
5. Controlled inspection by AI agents.

### Tooling Needs

1. Trace/log/metric APIs.
2. Source mapping from runtime events to declarations.
3. Observability query tools.
4. Redaction and access-control integration.

## Durable Workflows

### Agent Tooling Fit

Workflows should allow agents to execute multi-step tasks safely.

They should support:

1. Durable progress.
2. Retrying.
3. Idempotency.
4. Mocked external dependencies.
5. Observable execution history.

### Engineering/Infra Fit

Workflows should be a standard-library feature built on effects.

They should support:

1. Durable steps.
2. Persistence.
3. Resumption.
4. Compensation or cleanup.
5. Integration with observability and data-retention rules.

### Tooling Needs

1. Workflow checker.
2. Idempotency checker or linter.
3. Workflow test runner.
4. Workflow history viewer.
5. Cloud/runtime adapter.

## Sandboxed And Resumable Execution

### Agent Tooling Fit

Agent scripts and tool calls should run in a sandbox by default. External access should be represented through explicit capabilities, effects, handlers, or tool context.

Interactive runs should support resumption, similar to IPython or notebook-style workflows.

They should support:

1. Resume an interrupted interactive session.
2. Preserve typed values and validated data where possible.
3. Track which effects/capabilities were used.
4. Re-run or skip previous steps intentionally.
5. Keep execution history inspectable by humans and AI agents.

### Engineering/Infra Fit

Production workflows should support durable resumption, similar to Vercel workflows or Temporal.

They should support:

1. Durable checkpoints.
2. Replay or recovery.
3. Idempotency boundaries.
4. Capability-stable resumption.
5. Observable execution history.

### Tooling Needs

1. Sandbox policy checker.
2. Capability declaration/inference report.
3. Interactive session store.
4. Durable checkpoint store.
5. Replay/resume debugger.
6. Execution history viewer.

## Serializable Closures

### Agent Tooling Fit

Serializable closures should let agent tools package computation safely, not just data.

They should support:

1. Tool callbacks that can be stored, passed, or resumed.
2. Client/server or agent/runtime function references.
3. Cache keys derived from code identity, arguments, and captured values.
4. Interactive resumption where captured state is preserved intentionally.
5. Safe movement across runtime boundaries without ambient authority.

### Engineering/Infra Fit

Serializable closures should support durable workflows, remote execution, and caching.

They should support:

1. Capturing code identity and closed-over values.
2. Validating that captured values are serializable.
3. Preserving effect and capability requirements across serialization.
4. Persisting continuations at resumable points.
5. Replaying deterministic workflow steps.

### Tooling Needs

1. Closure capture analyzer.
2. Serializable-value checker.
3. Code identity/hash generator.
4. Effect/capability capture report.
5. Runtime boundary checker.
6. Closure resume/replay debugger.

## Incremental Computation

### Agent Tooling Fit

Incremental computation should help agent tools avoid repeating expensive work when only part of the input or environment changed.

It should support:

1. Dependency-aware caching for tool calls.
2. Reuse of intermediate results in interactive sessions.
3. Clear invalidation when inputs, captured values, or dependencies change.
4. Explainable cache hits and misses for AI agents and human reviewers.

### Engineering/Infra Fit

Incremental computation should make distributed systems more efficient and easier to reason about.

It should support:

1. Tracking dependencies between computations and data.
2. Recomputing only affected outputs.
3. Integrating with serializable closures for cache keys.
4. Integrating with workflows for resumable and deterministic execution.
5. Integrating with observability so invalidation and recomputation are visible.

### Tooling Needs

1. Dependency graph builder.
2. Cache key generator.
3. Invalidation checker.
4. Incremental recomputation planner.
5. Cache/recompute trace viewer.
