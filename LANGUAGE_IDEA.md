# AI-Oriented Language Idea Log

## Core Direction

Design a programming language aimed at making software easier for AI systems and humans to reason about, generate, validate, and test.

The language should feel like Rust and Go expressed through Python-like syntax: indentation-based structure, compact declarations, explicit types, simple data modeling, traits for shared behavior, and strong compile-time checks.

The main use case is quick AI-assisted testing. The language should let an AI write less code while exposing more intent. Correctness should come from static type checking, property-based testing, contracts, and built-in mock/test data generation from schemas.

The language has two primary scenarios:

1. Interactive scripts and tool calls inside AI agents.
2. Engineering and infrastructure code generated by AI.

The primary human workflow is reviewing AI-generated code. The language should therefore optimize for reviewability: visible intent, explicit behavior, compiler-checkable structure, and machine-readable diagnostics that help AI agents repair mistakes.

## Why A Language Instead Of A Library Stack

A TypeScript stack (Effect-TS, schema libraries, fast-check, Temporal) covers pieces of this feature list, but as separately designed libraries glued together at runtime:

1. Effects, schemas, contracts, and tests cannot check each other across library boundaries; an integrated compiler can.
2. Library-level effect tracking is encoding-heavy (generators, branded types) and produces diagnostics in terms of the encoding, not the intent — hostile to both human reviewers and AI repair loops.
3. Sandboxing and capabilities cannot be enforced by a library running inside an ambient-authority runtime.
4. Each library carries its own mental model, and the integration cost lands on every user and every generated program.

The language exists to provide the integrated solution: one semantic model where effects, validation, contracts, tests, tools, and workflows are checked together and produce unified machine-readable diagnostics.

## Initial Feature Set

1. Whitespace indentation based structure, similar to Python.
2. Structs instead of classes.
3. Trait-based methods and shared behavior.
4. `Result[T, E]` for error handling, plus an effect system for dependency injection, capabilities, suspension, handlers, and resumable runtime behavior.
5. Built-in schema validation.
6. Schema-based automatic test data generation.
7. Property-based testing as a first-class workflow.
8. Function contracts and invariants.
9. Struct embedding, similar to Go.
10. Garbage collection.
11. Sandboxed execution with explicit capabilities by default.
12. Execution resumption for interactive sessions and durable workflows.
13. Serializable closures for movable, cacheable, and resumable computation.
14. Incremental computation for dependency-aware caching and partial recomputation.
15. Built-in list and map collection types with literals.
16. Built-in tuple values and tuple types.
17. Primitive types for booleans, width-explicit signed and unsigned integers, width-explicit floats, strings, and chars.

## Current Design Decisions

1. Syntax should be indentation-based and lightweight. Block-introducing headers use a trailing `:`, and simple definitions may put the body on the same line, such as `fn test() -> void: println("hi")`.
2. The semantic feel should combine Rust and Go, not Python's dynamic object model.
3. The type system should be static.
4. Effects should be explicit in function signatures.
5. The language should prioritize concise AI-generated code, readable intent, and testability.
6. Correctness should be reinforced by type checking, property tests, contracts, invariants, and generated mock data.
7. Absence should follow Swift's design: values are non-optional by default, optional values are explicit, and `nil` is only valid for optional types.
8. Syntax design should come before implementation.
9. Function contracts should use direct `require` and `ensure` sections, inspired by NimContracts, without a wrapping `contract` block.
10. Functions with contracts should not use an explicit `body` section. The executable body starts after the contract sections by dedenting one indentation level.
11. Contracts should not be proven at compile time. Contract expressions should be typechecked, and possible contract failure should be tracked as its own effect.
12. Optional types should use Swift-style spelling, such as `string?`.
13. Failed `require` and failed `ensure` should be distinct effects, because they represent caller obligation failures and callee obligation failures.
14. Contract checks should run in test/debug builds by default, and should be configurable to run in production.
15. Dependencies should be modeled as signature requirements, not as special declarations. A dependency can be an ordinary trait or capability, such as `Database`, that appears in a function's `$` requirement row and is implemented by handlers.
16. Validation should use two styles: lightweight annotations for minimal inline constraints, and external derivation/override blocks for richer or extendable metadata. The exact block syntax remains open.
17. Property tests should automatically generate test data from schema information.
18. Property-test syntax should be designed separately from the core language syntax.
19. The language should support AI-agent tool definitions with typed inputs, validation, descriptions, examples, auth/context/access-control metadata, and references between tools.
20. The language should include built-in observability primitives for logging, tracing, and metrics, especially for AI operations.
21. Durable persistence and workflow execution should be provided by the standard library, built on effects, in the style of systems like Vercel workflows or Temporal.
22. WebAssembly is the sole compilation target. hd-lang uses Wasm GC for managed language values and WASI as its host interface. The concrete WASI version and component ABI remain implementation decisions.
23. Tool definitions should replace JSON schema/OpenAPI-style specs when using this language's infrastructure, and generate those specs when interoperating with existing tooling.
24. Infrastructure awareness should lean toward built-in code inspection: resource definitions can be derived from code, then deployed or synced to cloud infrastructure.
25. Raw production data should not be accessible through the language. Observability signals such as logs and traces should be accessible through controlled language/runtime features.
26. Struct data should be able to express declarative data-retention and cascade behavior, such as deleting posts when a user is deleted. This should use the general annotation/derivation facet model, not a standalone retention syntax.
27. The language should be function-first. Normal structs and functions are primary; system information should be produced through `annotate`, with registration performed explicitly.
28. Registration annotations should support compact one-line forms and indented metadata blocks for heavier cases.
29. The primary reader is a human reviewing AI-generated code.
30. The language should be a normal general-purpose programming language with strong AI and infrastructure features, not primarily a specification DSL.
31. Annotation metadata should not create distinct static subtypes by default. Base type identity remains normal, and validators are used by tooling and runtime checks.
32. Validation annotation syntax should feel Zod-like where composition is useful, with custom validators implemented as normal functions.
33. For validated data types, tooling should generate runtime validators, JSON Schema, TypeScript types, test data generators, serializers/deserializers, and documentation.
34. Invalid test data generation is not needed initially.
35. Code should run in a sandbox by default, with capabilities explicitly declared, granted, or handled.
36. The language/runtime should support execution resumption in two modes: interactive session resumption, similar to IPython/notebook workflows, and durable workflow resumption, similar to Vercel workflows or Temporal.
37. Validated newtypes are supported through explicit branding: a `brand` type is a distinct static type whose values are constructed through validation ("parse, don't validate"). Decorated declarations keep base type identity and never refine; there is no annotated type syntax in the current design.
38. Effect polymorphism should support propagating callback effects and removing effects handled internally, such as `e - Logger`, without necessarily committing yet to full row polymorphism.
39. Annotation facets should be able to define their own annotation terms. For example, `Retention` might define terms such as `ownerId` and `deleteWhen`, similar to validation facets defining terms such as `email` or `max_len`.
40. The annotation protocol uses ordinary runtime shape values plus traits and implementations. `Annotation` defines the annotation kind's uniform `Info`; `Annotate[A]` records that a concrete target provides information for `A`. Local metadata uses open traits such as `FieldMetadata[T]`, `VariantMetadata`, and `ParamMetadata[T]`; aggregate derivation remains in `StructAnnotator`, `EnumAnnotator`, and `FuncAnnotator`. Composition is strictly bottom-up.
41. `annotate Facet for Target` is structural syntax that generates the same conformance as `impl Annotate[Facet] for Target`, while additionally supporting field/variant overrides of existing members. A direct impl manually constructs the complete information value. Both forms occupy one coherence slot. Function parameter assignment overrides remain deferred in v1.
42. Only one `annotate Facet for Target` block is allowed for an exact facet/target pair in a package, and annotation blocks are package-global. A facet is open across target types: packages may add new exact cases such as `annotate Validation for Email` or `annotate Validation for list[Entry]`. A library's concrete case is authoritative and cannot be overridden downstream, but cases for other target types do not close the facet.
43. Annotation derivation reads already-computed child information and attached metadata values from shapes. For example, `DatabaseSchema.map_field(field, type_info)` combines the field type's annotation information with `field.metadata(MaxLen)` populated by `annotate User`. The compiler passes type information explicitly; `map_field` does not restart resolution internally.
44. There is no decorator syntax. `annotate Target` assigns homogeneous lists of dynamic metadata trait values to existing fields, variants, or parameters and lowers them into declaration-shape metadata. For a field of type `T`, the expected collection type is `list[FieldMetadata[T]]`; constructor calls, helper calls, named values, and reusable lists remain ordinary values.
45. `annotate Validation for User: pass` requests default aggregate derivation and generates `impl Annotate[Validation] for User`; `pass` means no structural result overrides. Runtime retrieval remains explicit: `Validation::annotation(User)` or `DatabaseSchema::annotation(User)` produces an ordinary runtime value such as `Validator` or `TableSchema`.
46. Generic field mapping resolves the annotation facet for the field's exact type. Resolution prefers an exact annotation such as `annotate Validation for Email` or `annotate Validation for list[Entry]`, then an attached struct/enum annotator for aggregates. The facet remains open because another exact target case can be added later; behavior when no case exists remains undecided.
47. Recursive annotation derivation should be automatic for every annotation kind. The resolver tracks active `(annotation, concrete target)` pairs and completed package-level implementations. Completed and non-recursive edges use ready `AnnotationRef[Info]` values; re-entering an active pair produces a deferred `AnnotationRef[Info]`. The common `Annotation` and `Annotate[A]` traits have no recursion hook, and information values do not need cases such as `Validator.Ref`. Recursive output stores `AnnotationRef[Info]` at recursive positions. Annotation information is memoized per package by annotation and concrete target.
48. A manual `lazy` field-metadata value inside `annotate Target` remains an optional candidate for requesting deferral even without a detected cycle. It would not change field storage, access, or type semantics. Automatic recursion detection is preferred; the exact consumer scope remains open.
49. Serializable closures are a runtime goal, but their semantics are deferred and outside the active language-tour design. Before choosing syntax or an API, the design must specify capture snapshots and aliasing, mutable captures, object graphs and cycles, code identity and compatibility, generic specialization, dependency rebinding, target portability, serialization failure, and execution guarantees. No `Serializable[fn(...)]`, function modifier, annotation, or inference rule has been accepted.
50. The runtime should support incremental computation: dependencies of computations should be tracked so derived results can be reused and only affected computations are recomputed when inputs, captured values, data dependencies, or code change. Cross-run caching is a related but separate mechanism with stricter identity requirements.
51. Annotator applicability is independent of declaration visibility. For example, `annotate Tool for get_user` can target either a module-private or `pub` function, `FuncAnnotator` does not impose visibility requirements, and annotation does not alter language-level visibility. Tool registration remains explicit.
51. The language has only two local binding forms: `:=` for short const bindings with type inference, and `let` for local variables that may be reassigned. `mut T` is a type modifier and is always written in the type position, including `let value: mut T`; the former `let mut value: T` spelling does not exist. An unannotated `let` infers the initializer's access type, fresh composite construction may infer `mut T`, and inference never upgrades an existing `T`. A composite `T` cannot be upgraded to `mut T`, while `mut T` may be viewed as `T`. `:=` is also an expression: it evaluates to the bound value and introduces the const name in the nearest enclosing block.
52. Built-in `list` and `map` collections should be part of the core language surface, with typed values, literals, and compiler/tooling awareness for validation, testing, serialization, and interop. A built-in set literal is not needed for now.
53. Built-in type names should be lowercase. Primitive scalar/data types should include `bool`, signed integers `i8`/`i16`/`i32`/`i64`, unsigned integers `u8`/`u16`/`u32`/`u64`, floats `f32`/`f64`, `string`, and `char`. There is no separate byte or bytes literal syntax for now.
54. Tuples are built into the language for lightweight grouped values. Tuple types and literals use `(T, U)`, one-element tuples use a trailing comma like `(T,)` and `(value,)`, the empty tuple is `()`, indexing uses numeric field access such as `point.0`, destructuring supports `x, y := point` and `let x, y = point`, and named tuples are omitted in v1 in favor of structs.
55. Struct literals should use type-name-plus-braces syntax, such as `User { id: "user_123" }`, to keep data construction visually distinct from function calls.
56. Struct embedding should use a bare type-name line inside the struct body, such as `Timestamps`, without an `embed` keyword. When initializing a struct with embedded fields, use the embedded type name as the literal key, such as `Timestamps: Timestamps { ... }`. Embedded-field name conflicts should follow Go-style promotion rules: direct promoted access is valid only when unambiguous, and conflicts require qualification through the embedded field.
57. Composite struct fields may store mutable reference permission with `field: mut T`; an ordinary `field: T` is a const edge. Mutation through a composite path requires a mutable root and `mut` on every composite edge crossed. A mutable outer root may replace a const field slot but cannot mutate the referenced child through that const edge. Initializing `field: mut T` requires a `mut T` value. Struct copy-update uses spread syntax in a typed literal, such as `User { ...user, display_name: "Ada" }`.
58. Field metadata uses functional value construction inside `annotate Target`, such as `email = [email(), max_len(80)]`.
59. Explicit `return` exists for functions, especially for early exits.
60. Function calls support named arguments using `name=value` syntax. Calls may mix positional and named arguments, but positional arguments must come before named arguments; no positional argument may appear after a named argument.
61. Function parameters can have default values. Defaults may use pure expressions and pure function calls, but cannot require effects, dependencies, or suspension.
62. Function overloading is not supported; each function name resolves to one declaration in a scope.
63. Generic function syntax should put generic arguments after the function name, such as `fn first[T](items: list[T]) -> T?`. Generic arguments are inferred at call sites when unambiguous, and callers can provide the full generic argument list explicitly, such as `first[string](names)`. v1 has no partial explicit generic arguments or placeholder generic arguments.
64. Traits describe shared behavior without classes. Trait implementations use `impl Trait for Type`, inherent methods use `impl Type`, trait methods use `self` or `mut self`, and generic constraints can use forms like `fn show[T: Display](value: T) -> string`.
65. Semantically, primitive types are passed by value and composite types are passed by reference. Structs, tuples, lists, and maps are composite types.
66. Trait implementation is explicit, not structural. A type does not implement a trait just because it has matching methods.
67. Trait bounds compose like Rust, such as `T: Display + Named`.
68. Traits can provide default method implementations.
69. Struct embedding promotes methods in the same spirit as fields. Promoted methods can be called when unambiguous, and unambiguous promoted methods can satisfy trait requirements for the outer struct. Conflicts require qualification through the embedded field or an explicit impl.
70. Dynamic dispatch follows Go interface style: use the trait name as a value type, such as `value: Display`, and method calls through that trait value dispatch to the concrete implementation at runtime. There is no `dyn` marker. `Any` is the built-in universal empty trait, analogous to Go's `any`, and every non-optional value type satisfies it automatically. `value: Any` is therefore an erased dynamic trait value, while generic bounds such as `T: Display` and `T: Any` use static dispatch.
71. Normal error handling is done with `Result[T, E]`, not effects. hd-lang pragmatically decomposes concerns commonly handled by algebraic effects into three related mechanisms: one-shot suspension, static requirement checking, and dependency injection. `fn!`, `Suspend[T]`, bang calls, polling, and cancellation manage one-shot suspended execution rather than general or multi-shot continuations. `$` requirement rows verify that dependencies are available; they are not primarily an authority or host-capability model. Contexts and providers select concrete implementations. At explicit dependency and suspension boundaries, the same source can execute with production, mock, sandbox, or replay providers and drivers; ordinary code outside those boundaries is not reinterpreted. Context access uses `$` operations with requirement keys as labels or arguments: `db, cache := $.use(Database, Cache)` retrieves providers, `$.with(Database=mock_db, Cache=memory_cache):` provides scoped requirements, and reusable contexts use row-indexed provider-map types such as `$.Context[Metrics + Cache]` with builders such as `$.context(Metrics=metrics, Cache=cache)` plus spread reuse like `$.with(Database=db, ...prod_context()):`. Context rows are unordered and unique by requirement key; duplicate providers cannot coexist, so construction/spread collapses duplicates with later bindings winning. Missing providers are compile-time errors. A function whose own body contains suspension points has a `!` suffix in its name, such as `fn get_user!(...)`, and a call with `!`, such as `db.get_user!(id)`, marks a suspension point. Dependency requirements and suspension are related but distinct; a requirement-polymorphic wrapper can expose callback requirements without itself being named with `!`.
72. Rust-style `?` propagation is supported for both optional values and `Result[T, E]`.
73. Closures use anonymous `fn(...) -> ...` syntax and capture values from lexical scope. There is no separate short closure syntax in v1; same-line closure bodies are allowed for single-expression closures, such as `fn(x: i32) -> i32: x + 1`. An inline closure may omit parameter and return types when its expected function type determines them; standalone or ambiguous closures require explicit signatures. Multiple multiline closures can remain inline as ordinary call arguments by parenthesizing each closure expression and placing the argument comma after its closing parenthesis. Shorthand argument closures using `$0`, `$1`, etc. are deferred. Closures that mutate captured locals have mutable function type `mut fn(...) -> ...`, and calling one requires the closure value itself to be mutable. Closures that capture dependencies or capabilities carry those requirements in their function type. Serializable-closure capture semantics remain deferred.
74. Numeric expressions support ordinary arithmetic operators (`+`, `-`, `*`, `/`, `%`, `**`, unary `-`) and integer bitwise operators (`&`, `|`, `^`, `~`, `<<`, `>>`). Integer `/` truncates toward zero. Integer overflow is always checked unless code uses explicit wrapping APIs. Shift counts can use any integer type, but must be non-negative and in range at runtime unless statically known. Operator precedence follows a Python-like shape, with primaries highest, then postfix propagation/suspension, exponentiation, unary, arithmetic, shifts, bitwise, comparisons, `and`, `or`, value-producing control flow, closures, and `:=` lowest.
75. Built-in list and map comprehensions use clause-first syntax with `=>`, such as `[for name in names if name.len() > 3 => name]` and `{for user in users if user.active => user.id: user}`.
76. The type system is static with local inference and explicit public boundaries. Structs and enums are nominal, tuples are structural, traits require explicit implementation, generic bounds use static dispatch, trait value types use Go-style dynamic dispatch, and nullability is explicit through `T?`.
77. Type aliases are transparent by default, using a spelling like `type UserName = string`. Nominal single-field newtypes use a distinct spelling, currently sketched as `type Mile(i32)`, construct with `Mile(10)`, and unwrap/cast back with base-type constructor syntax such as `i32(miles)`. No `.value` or pattern matching access is needed for now.
78. Lower-precision integers can be assigned to higher-precision integer types through implicit widening. Higher-to-lower precision conversion requires an explicit cast using constructor-style syntax such as `i16(value)`.
79. Variadic functions use vararg parameters such as `values: i32...`. Varargs must be the final positional parameter. Call sites can spread list values positionally with `values...`; spread syntax is positional only. A named vararg accepts a list, such as `values=items`.
80. Variadic generics use ordered type parameter packs, sketched as `Args...`, so higher-order functions can preserve exact argument lists. Minimal v1 supports pack expansion in function types, vararg parameters, tuple types, call arguments, and type or expression patterns. A pattern such as `Suspend[Ts]...` repeats once for every type in `Ts...`, while `(Ts...)` forms the corresponding heterogeneous tuple type. Packs referenced by the same repeated pattern expand in lockstep and must have equal lengths. Expansion is compile-time and does not create a runtime collection. General pack mapping, filtering, indexing, splitting, and arithmetic remain unsupported.
81. Integer literals always default to `i32` when there is no expected type. When there is an expected numeric type, integer literals are range checked against that type.
82. Modules are path-inferred from files under the package source root. There is no required `module` or `package` declaration. Packages use `hd.toml`, with `src` as the default source root. Directories define submodule namespaces only when they contain a required `mod.hd` file, which acts as the directory module/public index. Visibility uses `pub`; imports use explicit roots: `pkg` for the current package, `std` for the standard library, `dep.<name>` for dependencies declared in `hd.toml`, plus `self`/`super` for relative imports.
83. `pass` is the general no-op expression and evaluates to `void`. In `annotate Annotation for Target: pass`, it means default derivation with no structural result overrides.
84. Unit tests use dedicated module-level blocks such as `test "parse a user":`. The test runner discovers these blocks directly; they are not annotations and do not require manual registration.
85. Assertions are ordinary functions in `std.testing`, not language constructs. They require an explicit `reason` string. Specialized functions such as `assert_equal(actual, expected, reason=...)` should preserve actual and expected values for structured diagnostics.
86. Property testing is deferred as a large library-level design. It must live in `std.testing`, not introduce dedicated property-test language syntax. Strategy representation, generated-value access, type- and annotation-based derivation, dependency injection, shrinking, replay, correlated inputs, stateful testing, and failure artifacts remain undecided.
87. Function generic parameters are erased at runtime by default. A parameter marked `reified`, such as `fn resolve[reified T]() -> T`, receives hidden runtime type metadata and may use `shape(T)`, runtime annotation lookup, type-directed dependency injection, and similar operations. Passing an outer generic parameter to a reified parameter requires the outer parameter to be reified as well. Reification does not require `inline`; the WebAssembly backend may specialize or remove descriptors only when observable behavior is preserved. In v1, `reified` applies only to function generic parameters.
88. Capabilities are ordinary dependencies. They use normal traits, `$` requirement rows, and `$.use`/`$.with`/`$.Context` operations; there is no separate capability declaration or type-system category. Every authority-bearing capability provider originates at the Wasm host boundary through WASI or an official runtime extension. A module cannot manufacture ambient filesystem, network, clock, randomness, secrets, or similar authority. User code may wrap or narrow injected providers, and test hosts may inject harmless implementations through the same dependency mechanism.
89. An entry point's transitive `$` requirement row is the authoritative capability/provider list. The compiler derives and verifies it from the call graph. Package and deployment manifests do not duplicate a separate permission list; host configuration only binds concrete providers and scopes to the derived requirement keys. Missing bindings fail before execution. Every host-backed standard-library service is exposed as a trait and accessed through the ordinary context system. The official hd runtime implements every standard capability and injects only those granted to the invocation; alternate hosts may support a declared subset and must reject an entry point whose requirements they cannot bind. Pure standard-library operations remain ordinary functions and do not require context.
90. Durable workflow execution should initially use deterministic replay over an append-only event history. When replay reaches a suspending `!` call whose completed result is already recorded, the runtime returns that result without repeating the operation. A new suspension records a command and pauses the run until its completion is appended. There is no `checkpoint` keyword and v1 does not serialize the machine stack. Workflow runs pin code identity, deterministic code between suspension points must replay consistently, external operations receive idempotency keys, and capability providers are rebound rather than serialized.
91. Interactive execution combines a live kernel with a deterministic cell journal. While the kernel remains alive, reconnecting reuses its current namespace without replay. Every successful cell atomically commits an execution record containing its cell/source/code identity, parent state, suspension events, state delta, and output. Crash recovery restores a serializable snapshot and replays later committed runs in actual execution order, reusing recorded `!` results. Editing and rerunning an earlier cell creates a new history branch and marks its previous descendants stale rather than silently rewriting historical state.
92. Observability is automatic at semantic runtime boundaries rather than at every function. Entry points, registered tool and RPC calls, workflow runs, interactive cell runs, suspending `!` operations, and runtime dependency/provider boundaries produce correlated telemetry. Ordinary helper functions are not automatically traced. `Observability` is an explicit dependency: compiler- or library-generated boundary adapters require it, and user functions that emit explicit telemetry list it in `$`. The generated adapter is the registered/deployed entry, so observability remains visible in the executable requirement graph without polluting the wrapped business function's signature.
93. Each execution task carries execution-local observability state containing the current span, scoped log fields, trace links, and related context. Child tasks inherit a forked context, lexical scopes restore previous values, and suspension/resumption preserves it. A boundary adapter creates a span, installs it as current, executes the wrapped operation, and ends the span from the operation's complete exit so success, `Result` failure at the boundary, defects, cancellation, and interruption can be represented. Explicit logs are enriched from the current context and automatically become events on the current span. Boundary lifecycle is represented by spans rather than duplicate start/end logs; unhandled errors, defects, retries, cancellations, and failed suspensions produce automatic runtime events.
94. The provisional v1 provider interface uses `Observability.sample(candidate) -> bool` plus `Observability.emit(event) -> void`. The runtime, not the provider or application, owns trace/span IDs, current-span context, lifecycle closure, enrichment, and replay suppression. Providers receive a normalized `Observation` stream containing span starts/ends, logs, metrics, and runtime events. Initial strategies include console formatting, in-memory recording for tests, fan-out, and a non-suspending buffered OpenTelemetry exporter. This interface is an initial draft and may be optimized later.
95. Incremental queries, cross-run result caching, and durable workflow replay are separate mechanisms. An incremental result is derived data that may be invalidated, a cache entry is reusable across executions only while its complete identity remains valid, and a recorded workflow result is a historical fact for one logical run. A suspending `!` call does not imply cacheability, and a `$` requirement identifies provider availability rather than a versioned data dependency.
96. The provisional incremental-computation direction is a native-feeling `std.incremental` library backed by runtime dependency tracking and existing language reflection/tooling, not a new `incremental` keyword. The library should expose explicit inputs and computations, while reads inside an incremental computation dynamically record the dependencies actually used. Conditional recomputation atomically replaces obsolete dependency edges.
97. Incremental computations can use ordinary hd-lang function typing to require write purity. A computation accepts a plain, non-suspending `fn`, not a `mut fn` or `fn!`, with no `$` requirements, mutable parameters, or mutable captures. The normal type checker enforces those restrictions transitively; no incremental-specific write-purity rule is needed. Local mutation of newly created, non-escaping values remains compatible with write purity. This does not prove referential stability because const bindings may observe mutation through other aliases; changing shared state must enter incremental computation through tracked or separately stable inputs.
98. The recommended initial runtime uses transactional input updates, lazy recomputation, topological stabilization, equality-based propagation cutoff, and a DAG with cycle diagnostics. External files, databases, HTTP resources, clocks, and similar inputs must enter through explicit tracked sources carrying stable revisions, digests, ETags, snapshots, or equivalent version tokens. Invalidation correctness is separate from freshness policies such as TTL or stale-while-revalidate.
99. Incremental graph inspection is part of the feature rather than optional debugging output. Tooling should expose code and input identity, runtime-observed dependencies and dependents, clean/dirty state, revisions, cache state, invalidation causes, timing, and enough provenance to answer `why stale`, `why recomputed`, `why not recomputed`, `upstream`, `downstream`, and `explain cache key`. Exact APIs, storage tiers, identity formats, keyed collection granularity, observation lifetime, and persistent/distributed caching remain deferred because incremental computation is a large design surface.
100. Primitive parameters are passed by value. Composite reference permission is part of the type: `T` is const and `mut T` is mutable. Mutable permission composes through locals, fields, generic arguments, function parameter types, and returns, such as `let user: mut User`, `friend: mut User`, `list[mut User]`, `fn(mut User) -> void`, and `-> mut User`. `mut self` remains receiver shorthand for `self: mut Self`.
101. Mutation through a composite path requires both a mutable root and mutable permission on every composite edge. Therefore `users: mut list[User]` can replace list elements but cannot mutate the referenced users, while `users: mut list[mut User]` can do both. A const root cannot mutate through nested `mut` edges. Multiple mutable aliases may exist; `mut` expresses permission, not ownership or exclusivity. Concurrency isolation remains separate.
102. The previous shallow const-binding design is retained as an alternative: const local bindings could be deliberately re-aliased through mutable bindings or containers, composite parameters used implicit `const T&`/`T&` behavior with `mut` before the parameter name, and fields had no `mut T` qualifier. It had a smaller surface but could not express nested, container, function, or return mutation authority uniformly.
103. An ordinary generic parameter denotes a complete type, including its access modifier. Generic storage uses `field: T` and can be instantiated as `Box[User]` or `Box[mut User]`; an unconstrained declaration such as `field: mut T` is invalid because `T` may already be `mut U`. Mutable generic bounds use `T: mut Any` for any mutable root type and `T: mut Trait` for a mutable root whose underlying type implements `Trait`. This allows generic code to prove that a `mut self` method may be called while preserving the complete inferred access-qualified type as `T`.
104. Generic type declarations use `+T` for covariance, `-T` for contravariance, and unmarked `T` for invariance. The compiler verifies polarity against the declaration's read-only fields and methods; function parameter positions reverse polarity. Variance conversions apply only to read-only outer views, while every `mut Generic[...]` view is invariant in its arguments. The built-in list element parameter is covariant, conceptually `list[+T]`, so `list[mut User]` can coerce to `list[User]`; `mut list[mut User]` cannot coerce to `mut list[User]`. A weakened view is not a snapshot and may observe changes made through another mutable alias.
105. `pub fn main` is the conventional default entry point for an executable package. It has no source-level parameters; arguments, environment, I/O, and all other host services are obtained from `$` context requirements. It follows the ordinary `!` suspension-name rule and may return `void` or `Result[void, E]`. `pub` controls hd-lang visibility but does not automatically create a Wasm export. Tools, workflows, and library-facing functions require explicit registration, which generates their host boundary adapters.
106. Registered Wasm boundaries initially accept only recursively boundary-safe structural values: primitive scalars, `string`, tuples, `list[T]`, `map[K, V]`, structs, enums, `T?`, and `Result[T, E]`. Every nested component must also be boundary-safe, and map keys must satisfy ordinary map-key rules. Maps are unordered by default; insertion and iteration order are not part of their value or boundary semantics. Mutable types, trait values, closures, and live runtime handles remain internal. `$` requirements are resolved by the host adapter rather than serialized as boundary arguments.
105. Calls support an indented trailing block only for a final zero-argument function parameter. `when(a, b): body` is sugar for passing `fn(): body` as the last argument, while a no-ordinary-argument call uses `transaction: body` without empty `()`. The compiler infers and checks the callback return type and behavior from the final parameter. Parameterized callbacks still require explicit `fn(...)` syntax, and only one trailing block is allowed.
106. `Any` is non-null. It accepts every non-optional value but not `nil`; `Any?` is the optional universal trait value and can contain `nil`, following the normal `T` versus `T?` rule. An optional `T?` cannot erase directly to `Any`, but can erase to `Any?`. `mut Any` is valid for an erased mutable composite reference, and does not itself expose mutation operations beyond those provided by an additional trait or a checked concrete-type operation.
107. A trailing block has ordinary closure-local control flow. `return` inside it exits the generated zero-argument callback and supplies that callback's return value; it never returns from the lexically enclosing function. Non-local return through a trailing block is not supported.
108. Suspending functions produce cold computations. `fn load!() -> T` is source-level sugar for a function that constructs `Suspend[T]`: `load()` captures arguments and caller-provided dependencies without entering the body, while `load!()` constructs and immediately drives the suspension. Nested bang calls are possible suspension points. `Suspend[T]` is the trait implemented directly by generated frames, providing polling and synchronous cancellation. Polling returns `Poll[T]`, either `Pending` or `Ready(T)`, and uses a polling-context waker. Each suspension represents one execution, with exclusive driving enforced by runtime panics rather than type restrictions. Competing drivers, reentrant polling, and driving after completion or cancellation panic; successive pending polls by the same driver are valid. Captured providers cannot be replaced at drive time. Cancellation is synchronous and repeated cancellation is harmless; cleanup cannot suspend. Source-level cleanup remains [backlog work](DESIGN_QUESTIONS.md#deferred-resource-cleanup-and-scope-exit). A separate `Task[T]` abstraction is deferred. Exact stored-value driving syntax, scheduling, structured scope representation, and combinator failure policies remain open.

## Contract Syntax Sketch

```text
fn divide(a: i32, b: i32) -> i32 $ require + ensure:
    require:
        a >= 0
        b > 0
    ensure:
        result * b <= a
        (result + 1) * b > a
    a / b
```

30. Primitive type v1: no convenience aliases such as `int`, `uint`, or `float`; use explicit-width numeric types. `decimal` is a standard-library type, not a primitive. `void` remains the spelling for functions that return no useful value. Integer literal range diagnostics include the invalid literal, target type range, and a suggested wider type. Narrowing diagnostics suggest explicit constructor-style casts such as `i16(value)`.
31. Tuple v1 is settled: structural tuples, Rust-style numeric field access, trailing comma for one-element tuples, `()` for empty tuple, destructuring bindings, and no named tuples.
32. Trait conflict diagnostics: when promoted methods conflict during trait checking, diagnostics should show the missing trait requirement, list the ambiguous promoted methods, and suggest an explicit impl or qualified embedded-method call.
32. Operator precedence and associativity follow the Python-like table recorded in the tour and syntax notes.
33. Comprehensions use clause-first syntax with `=>`, such as `[for user in users if (label := user.name.trim().lower()) != "" => label]`. Multiple `for` clauses are allowed and run left to right. Later clauses can use earlier names, `if` filters at the point where it appears, and later clauses are not visible to earlier clauses. There is no separate `let` clause; local names come from `:=` binding expressions. If a map comprehension produces the same key more than once, the later value wins. Comprehensions cannot contain suspension points.
34. Module/package v1: path-inferred modules, `hd.toml`, required directory `mod.hd`, explicit `pkg`/`std`/`dep`/`self`/`super` import roots, no import or re-export cycles, and only module-private plus `pub` visibility.
35. Loops with `else` can be value-producing expressions: `break value` produces the loop value on early exit, and the `else` value is used when the loop finishes normally. `break value` is only valid in a value-producing loop with `else`; statement-only loops use plain `break`.
36. `match` arms use `pattern => expression`, and `_ => expression` is the fallback arm spelling. Enum payload patterns use call-style parentheses, such as `Expr.IntLit(value) => value`, not brace destructuring. Payload patterns follow the same positional/named convention as calls: positional patterns first, then named patterns. Only `field=pattern` counts as a named pattern. Bare identifiers bind new names, and positional binding names do not need to match payload field names, such as `Expr.Add(l, r)` for fields named `left` and `right`. Literals match exact values.
37. `else if` is one direct conditional-chain syntax form, not a nested `else` block containing a separate `if`.
38. Enum payload variant declarations use compact `Variant(field: type)` syntax in v1. Large payloads should use a separate struct.
39. Enum variant patterns in `match` arms must be qualified with the enum name, such as `JobStatus.Queued`, even when the matched value's type is known.
40. Enums support generic algebraic data types, recursive enum definitions, and GADT-style variants with explicit result types, such as `IntLit(value: i64) -> Expr[i64]`. A variant can also refine the enum type while passing data to an enum-level constructor, such as `IntBox(n: i64) -> Box[i64](n)`. Pattern matching on a GADT-style variant refines the enum type parameter inside that arm, so `Expr.IntLit` can refine `Expr[T]` to `Expr[i64]` for arm-local type checking.
41. `Result` values are constructed with capitalized helper constructors: `Ok(value)` and `Err(error)`.
42. Enums can declare constructor parameters for data shared by every variant, including unnamed parameters such as `enum StatusCode(i32):`. Enum constructor definitions and calls follow the same parameter conventions as functions: unnamed positional parameters/arguments first, then named parameters/arguments. Variants can call the enum constructor in their result expression, such as `NotFound -> StatusCode(404)`.
43. Missing child annotations remain an open static-policy question. A candidate `MissingAnnotationPolicy` trait, with policy types such as `Require` and `Ignore`, could let a facet choose compile-time rejection or omission before runtime mapping. No default, granularity, or syntax has been selected, and runtime `map_field` cannot produce compiler errors.
44. Allowing arbitrary traits to opt into structural awareness of their implementation targets remains a speculative extension. It is not required for annotations: `annotate Facet for Target` supplies structural implementation sugar and `annotate Target` supplies member-shape metadata sugar.
45. Decorator syntax such as `@max_len(320)` may be considered as a future locality shorthand for member metadata. It is not part of the current design and, if added, must lower exactly to an equivalent `annotate Target` entry with identical metadata trait checking and runtime behavior.
46. Deterministic cleanup and scope-exit syntax are explicitly outside the MVP. The backlog should compare protocol-owned RAII/`Drop` or `using`, general lexical `defer`/`errdefer`, and Python-style `with`. A promising but unaccepted hybrid is protocol-owned cleanup for resource types plus Zig-style block-scoped `defer` as an escape hatch. Go-style function-scoped `defer` is not preferred because cleanup registered in a loop survives until function exit. The backlog must also solve resource escape: the current shared-reference and `mut` model cannot detect an alias stored globally, returned, captured, or placed in another object before the resource is disposed at scope exit.
