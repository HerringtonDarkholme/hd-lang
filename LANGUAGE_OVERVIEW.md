# Language Overview

This language is a general-purpose, statically typed language designed for humans reviewing AI-generated code.

It should feel like Rust and Go semantics with Python-like indentation: explicit types, structs instead of classes, traits for shared behavior, simple data modeling, visible effects, and strong compiler feedback.

The core goal is to make intent visible enough that humans and AI agents can understand, verify, test, and operate code.

## Primary Use Cases

### AI Agent Scripts And Tool Calls

The language should work well as an interactive scripting and tool-call language inside AI agents.

It should support:

1. Typed tool inputs and outputs.
2. Validation and sanity checks for tool data.
3. Generated JSON Schema, OpenAPI, MCP definitions, and TypeScript types.
4. Tool descriptions, examples, auth/context/access metadata, and cross-tool references.
5. Sandboxed execution with explicit capabilities.
6. Resumable interactive execution, similar to IPython or notebook workflows.

### Engineering And Infrastructure Code Generated By AI

The language should also work for real engineering and infrastructure code generated by AI and reviewed by humans.

It should support:

1. Compiler-visible effects, errors, dependencies, and capabilities.
2. Built-in mocking and dependency injection through effects and handlers.
3. Design by Contract with `require`, `ensure`, and `invariant`.
4. Property-based testing with generated valid test data.
5. Built-in observability: logging, tracing, and metrics.
6. Durable workflows via standard-library effects.
7. Code-derived infrastructure awareness.

## Language Shape

The language is function-first, not system-first. Normal structs, functions, and tools are primary. System registration is attached through annotations or decorator-like metadata.

```text
@tool
    description "Fetch a user by ID."
    context AuthContext
fn get_user(id: UserId) -> User !db !not_found !access
    access
        require auth.can("user:read")
    user := perform db.get_user(id)
    user?
```

Core language traits:

1. Static typing.
2. Python-like indentation.
3. Structs, no classes.
4. Traits for shared behavior.
5. Struct embedding, similar to Go.
6. Garbage collection.
7. Swift-style optionals, such as `String?`.

## Validation And Annotation Model

Validation metadata does not create distinct static subtypes by default. Base type identity remains normal. Validators are used by tooling and runtime checks.

Lightweight inline annotations are used for simple constraints:

```text
struct User
    id: UserId
    @email
    @max_len 320
    email: String
```

Richer metadata uses general annotation facets:

```text
annotate Validation for User
    email: email.max_len(320)

annotate DatabaseSchema for User
    email: varchar(320).unique()

annotate UI for User
    avatar: ProfileImage.rounded(size: 40)
```

Retention also uses annotation facets:

```text
annotate Retention for Post
    userId: ownerId
    policy: deleteWhen(User.deleted)
```

Facet terms such as `ownerId`, `deleteWhen`, `email`, or `max_len` belong to their facet. They are not global language keywords.

## Effects, Capabilities, And Handlers

Effects are explicit in function signatures:

```text
fn load_user(id: UserId) -> User !db !not_found
```

Effects can model:

1. Dependencies.
2. Errors.
3. Contracts.
4. Observability.
5. Workflows.
6. Sandbox capabilities.

Handlers provide dependency injection and mocking:

```text
effect db
    fn get_user(id: UserId) -> User?

handler mock_db for db
    fn get_user(id: UserId) -> User?
        User(id: id, name: "Test User")
```

Effect polymorphism should support propagating callback effects and removing internally handled effects:

```text
fn handle_log[e](callback: fn(String) -> Void !e) -> Void !(e - log)
    with logger
        callback("str")
```

This means `handle_log` handles `log` and propagates the remaining callback effects.

## Contracts

Contracts use direct `require` and `ensure` sections. There is no wrapper block.

```text
fn divide(a: Int, b: Int) -> Int !require !ensure
    require
        a >= 0
        b > 0
    ensure
        result * b <= a
        (result + 1) * b > a
    a / b
```

Contracts are typechecked but not statically proven. They run in test/debug builds by default and can be enabled in production. Failed `require` and failed `ensure` are distinct effects.

## Testing

Property-based testing is a first-class workflow in the tooling.

The language should generate valid test data from validation and annotation metadata. Invalid data generation is deferred for now.

Test syntax is intentionally designed separately from core language syntax.

## Runtime Features

The runtime should support:

1. Sandboxed execution by default.
2. Explicit capabilities.
3. Serializable closures.
4. Incremental computation.
5. Interactive execution resumption.
6. Durable workflow resumption.

Serializable closures package code plus captured environment so computation can be stored, moved across runtime boundaries, cached, or resumed.

Incremental computation tracks dependencies between code, inputs, captured values, data reads, and outputs so cached results can be reused and only affected computations recompute.

## Compilation Targets

The first compilation targets should be:

1. JavaScript.
2. WebAssembly.

## Summary

This is a statically typed, Python-indented, Rust/Go-inspired language for AI-generated systems, where effects, validation, contracts, tools, mocks, workflows, observability, sandboxing, and runtime dependency tracking are integrated into one compiler-checked model.
