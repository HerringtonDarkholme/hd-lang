# Decimal

Status: design proposal, 2026-10-28; domain: standard library exact-decimal API; not accepted.

This proposal addresses [#840](https://github.com/HerringtonDarkholme/hd-lang/issues/840).
It adds one `std.decimal.Decimal` value with a fixed 128-bit representation.
The [checked package](decimal/) contains every proposed signature and its usage examples.

## Proposal

`Decimal` stores a 96-bit unsigned coefficient, a sign, and a scale from 0 through 28.
It follows C# `decimal` and Rust `rust_decimal`, rather than allocating an arbitrary-size integer.
Arithmetic has bounded memory and predictable Wasm code; parsing never silently rounds input.

```text
use pkg.decimal.{Decimal, RoundingMode}

fn invoice(unit_price: Decimal, quantity: i64, tax_rate: Decimal) -> Decimal:
    subtotal := unit_price * Decimal::from_i64(quantity)
    tax := subtotal * tax_rate
    (subtotal + tax).round(2, .NearestEven)
```

## Open questions

1. Approve fixed 128-bit storage rather than arbitrary precision? **Recommended: yes**, for bounded Wasm cost.
2. Approve exact JSON strings rather than JSON numbers? **Recommended: yes**, to survive binary64 consumers unchanged.
3. Is a 12 KiB optimized-Wasm budget for the invoice surface acceptable? **Recommended: yes**, measured before implementation merges.

## Problems it solves

| Today | With `Decimal` |
| --- | --- |
| `f64` makes `0.1 + 0.2` inexact | Base-10 input and arithmetic use a base-10 coefficient and scale |
| Integer cents cannot represent rates or currencies with three minor digits | Each value carries scale 0 through 28 |
| Callers invent rounding conventions | Five named modes make settlement policy visible |
| A JSON number can be rounded by a binary64 consumer | Serde writes and reads the canonical decimal text as a string |

## How it works

### Representation and range

`Decimal` is 16 bytes: a 96-bit coefficient plus a 32-bit flags word holding sign and scale.
Its values are `coefficient / 10^scale`, with scale 0 through 28.
Zero has one sign; equality and ordering compare numeric values, not stored scale.

The largest magnitude is `79228162514264337593543950335`.
Trailing zeros are retained, so parsing `12.30` and displaying it again gives `12.30`.
`normalize` is deliberately absent: callers should not change wire or display scale accidentally.

### Arithmetic and rounding

`+`, `-`, `*`, `/`, `%`, and unary `-` return `Decimal`.
Overflow and division by zero panic with the same categories as primitive arithmetic.
Addition and subtraction align scales; multiplication starts with the sum of operand scales.

When an exact operator result does not fit, it drops the fewest low decimal digits needed to fit.
That internal fit rounding is nearest-even.
Division emits digits until the remainder is zero or scale 28 is reached, subject to coefficient fit.
It trims only trailing zeros generated by division, so `1 / 2` is `0.5` and `1 / 3` has 28 fractional digits.

`divide(rhs, scale, mode)` is the explicit settlement atom.
It produces the requested scale, using the selected mode.
`round(scale, mode)` reduces a value to at most that scale; it does not pad a lower-scale value.
Both panic when `scale` exceeds 28.

| `RoundingMode` | Result |
| --- | --- |
| `NearestEven` | nearest value; a tie goes to an even retained digit |
| `NearestAwayFromZero` | nearest value; a tie goes away from zero |
| `TowardZero` | discard removed digits |
| `TowardNegativeInfinity` | next value toward negative infinity |
| `TowardPositiveInfinity` | next value toward positive infinity |

### Text and serde

`Parse` accepts an optional sign, one or more ASCII digits, and an optional `.` followed by digits.
It rejects whitespace, separators, exponents, empty fractional parts, scale above 28, and out-of-range coefficients.
Parsing is exact: extra fractional digits are an error, never a rounded value.

`Display` writes ordinary decimal text without an exponent and retains stored trailing zeros.
`Serialize` calls `Serializer.text`; `Deserialize` reads text and applies `Parse`.
Thus JSON is `"12.30"`, not `12.30`.

The string choice fits hd's current serde data model without changing every serializer.
It also avoids RFC 8259's warning that consumers commonly limit JSON numbers to binary64 precision.

### Public surface

| Item | Purpose |
| --- | --- |
| `Decimal` | fixed 128-bit decimal value |
| `Decimal::from_i64` | exact widening from an integer |
| `Decimal.round` | reduce fractional digits with an explicit mode |
| `Decimal.divide` | divide at a caller-selected scale and mode |
| `RoundingMode` | two nearest and three directed policies |
| `ParseDecimalError` | invalid grammar or out-of-range input |
| Standard traits | `Parse`, `Display`, `Debug`, `Eq`, `PartialOrd`, `Ord`, `Hash`, arithmetic operators, `Serialize`, `Deserialize` |

## Cost

| Component | Cost |
| --- | --- |
| Value | 16 bytes, copied like other hd values |
| Heap | none for arithmetic; parsing and display allocate their returned text only |
| Unused program | 0 Wasm bytes: ordinary std functions remain unreachable and are not linked |
| Invoice program | implementation budget: at most 12 KiB optimized Wasm over the same `i64`-cents program |
| Compile time | one ordinary std module; no compiler-known name or intrinsic |
| Web compiler | implementation budget: at most 4 KiB gzip from the bundled std source, under the 2 MB cap |

This PR contains signatures with `panic("todo")` bodies, so it cannot honestly measure implementation code.
The implementation gate builds the package's invoice example twice, with `Decimal` and `i64` cents,
and reports total bytes, function count, and code-section bytes before accepting the 12 KiB budget.

## Appendix A: Stress test

The checked examples cover invoice accumulation, a percentage rate, a discount, negative refunds,
all five rounding policies, explicit-scale division, remainder, ordering, and JSON round trips.

Adversarial cases shape these rules:

- `0.005` rounded to two digits differs under `NearestEven` and `NearestAwayFromZero`.
- `-0.001` distinguishes both directed infinity modes from `TowardZero`.
- `1 / 3` requires a division policy even though neither input has fractional digits.
- `79228162514264337593543950335 + 1` must panic instead of wrap.
- `0.00000000000000000000000000001` parses; one more fractional digit is an error.
- `1.00 == 1.0`, while both values retain their own display scale.
- JSON `"79228162514264337593543950335"` survives JavaScript; a JSON number does not.

The fixed design loses arbitrary precision and exact non-terminating division.
That is intentional: `BigInt` and arbitrary-precision decimal remain package concerns.

## Appendix B: Prior art

### C# `decimal`

```csharp
decimal subtotal = 19.95m * 3;
decimal total = decimal.Round(subtotal * 1.0825m, 2, MidpointRounding.ToEven);
```

.NET stores a 96-bit integer, sign, and scale 0 through 28 in 128 bits.
Its five `MidpointRounding` modes separate nearest rounding from directed rounding.
hd takes that bounded representation and policy set, but uses culture-neutral parsing.
[Representation](https://learn.microsoft.com/en-us/dotnet/api/system.decimal.-ctor),
[rounding modes](https://learn.microsoft.com/en-us/dotnet/api/system.midpointrounding).

### Java `BigDecimal`

```java
BigDecimal subtotal = new BigDecimal("19.95").multiply(new BigDecimal("3"));
BigDecimal total = subtotal.multiply(new BigDecimal("1.0825"))
    .setScale(2, RoundingMode.HALF_EVEN);
```

Java pairs an arbitrary-size unscaled integer with a signed scale and requires a rounding contract for many divisions.
hd takes explicit scale and mode for settlement division, but rejects unbounded allocation in its one std decimal.
[BigDecimal](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html).

### Rust `rust_decimal`

```rust
let tax = Decimal::from_str("3.4395")?;
let due = tax.round_dp_with_strategy(2, RoundingStrategy::MidpointAwayFromZero);
```

`rust_decimal` uses the same 96-bit coefficient and 0-through-28 scale, preserves trailing zeros,
and offers explicit rounding strategies and string serde.
hd takes those ergonomic choices but exposes fewer constructors and no feature-dependent wire form.
[crate API](https://docs.rs/rust_decimal/latest/rust_decimal/).

### JSON

```json
{"amount":"79228162514264337593543950335"}
```

RFC 8259 permits large numbers but warns that common consumers limit range and precision to binary64.
An exact decimal string is less convenient for generic numeric tools, but it round trips through those consumers.
[RFC 8259, Numbers](https://www.rfc-editor.org/rfc/rfc8259#section-6).

## Appendix C: Alternatives considered

**Arbitrary precision.** Java-style `BigDecimal` makes finite operations exact until an explicit rounding point.
It adds allocation, variable-time arithmetic, a larger implementation, and no fixed Wasm cost.

**Integer minor units.** This is excellent for one known currency but does not cover rates, measurements,
or currencies with different minor-unit counts. It remains the smallest choice for applications that need only cents.

**JSON numbers.** They look natural and match mathematical JSON producers.
They need a new decimal scalar in hd's serde protocol or a JSON-only escape hatch, and binary64 consumers lose values.

**A decimal literal.** A new syntax or compiler-known suffix would improve constants.
This proposal stays an ordinary std module; text parsing is sufficient until real code proves literal friction.

## Appendix D: Today in hd

Primitive integers and binary floats are in `std.num`.
Floats parse decimal text by rounding to binary and display the shortest round-trip text.
JSON numbers store `i64`, `u64`, or finite `f64`; serde has only integer, float, and text scalar calls.

The proposal adds no language rule, intrinsic, or compiler-known name.
Its highest-cost change is an ordinary core-library addition, the cheapest class in the repository's design order.

## Appendix E: Implementation phases

1. Add the representation, exact parse/display, integer construction, equality, and order; test boundaries and scale.
2. Add add/subtract/negate and normalized comparison; test mixed scales and overflow.
3. Add multiply/divide/remainder and all rounding modes; test ties, signs, scale 28, and zero division.
4. Add serde as text; test JSON string round trips and reject JSON numbers.
5. Measure optimized Wasm against `i64` cents; stop for owner review above the 12 KiB budget.

No grammar, inference, pattern, ownership, runtime-host, or compiler-cache change is needed.
Conformance belongs in the stdlib tier when the proposal is accepted.
