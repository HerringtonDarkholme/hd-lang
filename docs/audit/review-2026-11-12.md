# Compiler, Language And Std Review, 2026-11-12

Status: an audit log. Nothing here is accepted behavior or an owner
decision. Every direction and question is a proposal for the owner.

This is a review of the compiler's architecture against
[goals.md](../compiler/goals.md), of sampled implementation quality against
the AGENTS.md commit bar, of the language design where it constrains the
compiler, and of `lib/std`. Each claim is marked **[V]** (verified in code,
by a run, or by a measurement) or **[I]** (inferred).

## 2. Verdict

The front half meets its targets at today's sizes: cold check of 10k lines
is 182 ms and edit-to-check p50 is 40 ms **[V]**. Conformance is 7459 of
7459 with no known failure **[V]**. The module graph, name resolution and
the trait solver's core scale linearly on every shape I tried **[V]**.

The back half does not meet the goals. It is whole-program, serial and
uncached, since per-function code caching left with the Wasm GC backend on
2026-10-20 **[V]**. The dev pipeline runs a link-time optimizer on every
build **[V]**.

The commit bar is not held mechanically. I reproduced two wrong
diagnostics on ordinary programs, one program that checks clean and then
fails to build, four native stack overflows, three exponential checks and
a dozen quadratic or cubic paths. The cost tests count checker fuel on
`hd check` only, so none of these could fail a test **[V]**.

Three daily-metric failures are not what they look like. `io-per-check`
measures the two-second settle window, `iterator-chain` exceeds a
spec-fixed limit, and the test set-up cost is the Node engine **[V]**.

`lib/std` is correct and faithful to its spec on about 150 boundary
inputs. Its costs to users are a thin first-reach API, two collection
families with different shapes, and protocols that do work per step
(§9).

The checker, TIR, ownership and reference-counting designs have their own
section, §13. Suggestions for TIR, the emitter, the optimizer and the
checker are in §14.

## 4. Architecture Against The Goals

### A1. The Back Half Is Whole-Program, Serial And Uncached

- Only `EntryKind::Link` is read or written for code
  (`hd_driver/src/lib.rs:9642`, `:11114`). `code_key`, `codepack_key` and
  `packhint_key` are called only by their own tests
  (`hd_cache/src/lib.rs:212`, `:232`, `:247`) **[V]**.
- `hd_wasm::build` emits and links the whole module in one `Link` task
  (`hd_wasm/src/lib.rs:746`). `par_map` has one call site in the compiler,
  for checker bodies (`hd_driver/src/lib.rs:7295`) **[V]**.
- The per-group code cache was removed in `dc358a56e`, "Remove Wasm GC and
  backend selection" **[V]**.

One private-body edit on generated packages whose `main` calls into every
module:

| Package | `hd check` after the edit | `hd build` after the edit | Cold back half |
| --- | --- | --- | --- |
| 10k lines, 78 files | 0.02 s | 0.17 s | 0.26 s |
| 200k lines, 1,545 files | 0.16 s | 3.30 s | 3.19 s |

User time equals real time in the build column, so the work is serial
**[V]**. The finding is that the last two columns are equal.

### A2. A Warm Check Costs O(Files), Not O(Change)

The `hd check` column above grows from 0.02 s to 0.16 s for the same
one-body edit **[V]**. Keys for every module are recomputed from the skims
and each `check` entry is looked up
(`crates/hd_cache/DESIGN.md` §5.5). At about 0.1 ms per file, the 50 ms
`edit-latency` target fails near 500 files **[I]**.

### A3. A Signature Edit Rechecks The Whole Use Closure

`check_key` lists the deep hash of every folder in a module's use closure
(`crates/hd_cache/DESIGN.md` §5.3). The `recheck-precision` metric rechecks
9 modules for a signature edit against a target of 3 **[V]**. Early cutoff
(#49) and per-body reuse are both "planned, not built" **[V]**. The closure
is needed because a solving context sees argument-owned impls from every
folder it reaches.

Go has the same shape, a per-package cache with no daemon. A Go dependent
rebuilds only when its inputs' content hashes change, which stops
propagation at an unchanged export
([Go build cache](https://pkg.go.dev/cmd/go#hdr-Build_and_test_caching)).
rustc gets the same effect per query
([incremental compilation](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html)).

### A4. Incremental Soundness Is Tested Thinly

`testing-the-compiler.md` §8.2 says the driver's scripted-edit test "went
with the Wasm GC backend … and has no replacement yet" **[V]**. The daily
metric applies 16 edits of 7 kinds to a small package. The design lists 22
edit kinds **[V]**. `HD_CACHE_VERIFY` is not built.

### A5. The Dev Pipeline Optimizes At Link

`Module::finish_link` runs `constants`, `static_values`,
`effect_free_calls`, `inline_counts` and the `locals` rule fixpoint for
every function, in every pipeline, on one thread
(`hd_wasm/src/module.rs:1957` to `:2053`) **[V]**. `dev-speed` is 1.22x
against an allowed 4x, so the dev tier spends compile time it is allowed
to save **[V]**.

The compiler has three rewriting layers: `hd_opt` body plans, the
`hd_tir::own` passes that splice bodies, and the 5,644-line Wasm peephole
in `hd_wasm/src/opt.rs` **[V]**. The peephole exists because emission gives
every TIR value a fresh local.

### A6. The Node Engine Sets Run And Test Latency

Warm runs with no edit, same machine, same cache:

| Workload | Node (default) | wasmtime |
| --- | --- | --- |
| `hd hello.hd`, start to output | 0.33 s | 0.02 s |
| `hd test`, 10 integration programs | 1.03 s | 0.15 s |
| `hd test`, 20 integration programs | 1.96 s | 0.29 s |
| `hd test`, 10 doc tests | 1.00 s | 0.07 s |
| `hd test`, 20 doc tests | 1.91 s | 0.15 s |

That is about 94 ms per test program on Node and about 13 ms on wasmtime,
and about 93 ms per doc test against about 7 ms **[V]**. The daily
failures `integration-test-perf` (130 ms, 119 ms; target 20 ms) and
`size-startup-heap` (45 ms; target 5 ms) are therefore engine costs
**[V]**. They are not costs of linking, and not costs of the rule that
each doc test is its own program (`module.test.doc.program`).

wasmtime is off by default because it triples the compiler's cold build
(`crates/README.md`). It also grows the binary from 18 MB to 33 MB
**[V]**, and the `disk` metric already fails at 20 MB.

### A7. Winch Can Compile The Current Output

The engine sets `wasm_gc(false)` and `wasm_tail_call(false)`
(`hd_run_wasmtime/src/engine.rs:169`) **[V]**. The wasmtime CLI compiled
the 2.56 MB dev module of the 200k-line package:

| Compiler | CPU time | Code size |
| --- | --- | --- |
| Cranelift, opt level 0 | 0.83 s | 5.1 MB |
| Cranelift, opt level 2 | 1.00 s | 4.7 MB |
| Winch | 0.23 s | 8.2 MB |

It compiles **[V]**. I did not run the result, since the CLI lacks hd's
host imports. Cranelift at level 0 saves only 17% over level 2 here.

### A8. Parallel Checking

Speedup is 1.79x on 4 threads against a 2.4x target **[V]**. On 14 cores,
cold check of 50k lines took 0.34 s against 0.77 s with `--jobs 1`. Two
decisions set the limit:

- Result and row inference for private functions runs serially per module.
  `crates/hd_tir/DESIGN.md` §4.13.1 says "most bodies of ordinary code omit
  their row, so M1 checks them on one core" **[V]**.
- The back half has no parallel step (A1).

The `concurrency` lines fail at 2.09x for 4 processes. Each process
defaults to one thread per core, capped at 8 (`cli.jobs.default`), so N
processes oversubscribe **[I]**.

### A9. The REPL Costs O(History) Per Input

The metric reports 73 ms per input at input 50 and 780 ms at input 1000
**[V]**. Through the browser build, with the same input shape:

| Input | Build time | Module size |
| --- | --- | --- |
| 25 | 40 ms | 1.0 KB |
| 100 | 59 ms | 2.5 KB |
| 200 | 85 ms | 2.5 KB |
| 400 | 168 ms | 2.5 KB |

The emitted module stays the same size, so the growth is driver work over
the earlier inputs, not code generation **[V]**. Which driver step grows
was not isolated.

### A10. The Browser Build

The driver owns no I/O and the cache store is synchronous, so the
one-thread build is sound by construction **[V]**. The fresh build is
6.54 MB raw and 2.15 MB gzip, under the 2.5 MB ceiling **[V]**. Two
gaps:

- The stepping scheduler exists and nothing calls it.
- The memory store is dropped whole at 64 MiB.

### Decisions That Are Expensive To Reverse

| Decision | Why it is expensive | Evidence |
| --- | --- | --- |
| RC in linear memory | Ownership passes, count elision, the cycle collector and loans depend on it: about 57k lines in `hd_wasm` plus `hd_tir/src/own*`. | Reversed once from Wasm GC, with 276 commits on `emit.rs` in three weeks **[V]** |
| Suspension as state machines | The spec fixes it: `req.lowering.sugar` says "a compiler-generated cold state machine". | **[V]** rule text |

## 6. Patterns

Ranked by total cost.

| # | Pattern | Cause in the architecture | Instances |
| --- | --- | --- | --- |
| 1 | Whole-program work on every build | the linear backend replaced a cached one | A1, A5 |
| 2 | Native recursion over input-shaped data | walkers written recursively, with caps instead of worklists | §5 Wrong Results, F8 |
| 3 | Work that fuel does not count | fuel counts expressions and proof nodes only | F8, F10 to F13 |
| 4 | In-place edits or linear scans inside a per-item loop | no shared index for "item by id" or "line by offset" | F12, F13; `.iter().position(` appears 19 times in `hd_check`, 11 in `hd_wasm` |
| 5 | Speculation that rechecks its argument | trial per candidate with no argument cache | F9, F10 |
| 6 | Half-migrated structure | fast backend replacement | dead cache kinds, `Skipped` passes, stale docs (§10) |

The in-tree tests cover the checker's width well:
`crates/hd_driver/tests/all/pathological.rs` runs 14 shapes under
`Goal::Analyze` and compares fuel at two sizes **[V]**. They do not build,
format, or count type nodes, and they enter the inferred-result chain from
a function, not a top-level statement.

### What Looked Sound

- **Module graph.** A 4,000-file fan-in, a 4,000-deep use chain and a
  4,000-step `pub use` chain each check cold in about 1.4 s, linear in n
  **[V]**.
- **Wide declarations.** 16,000 structs and functions in one module:
  0.57 s. An 8,000-variant enum with a full `match`: 0.16 s. 8,000 methods
  on one type, each called: 0.36 s **[V]**.
- **Solver core** (agent, read): recursion is capped by `LEVELS = 65`; the
  memo stores a height, so a hit overflows the depth limit exactly when a
  fresh proof would; `OutOfFuel` is never stored; lookup is by
  `(trait, head key)` bucket with binary search.
- **Trail rollback** is by length marks and an undo log; nothing is cloned
  per trial (`hd_check/src/trial.rs:240` to `:370`).
- **Discipline.** Non-test code has no `unwrap`. `hd_wasm` carries 159
  `ruled out:` notes against 215 `expect`s. `hd_cli` has 31 `expect`s and
  no note; `hd_check` has 47 against 16 **[V]**.
- **Determinism.** Fixed-seed hash maps and the sort wrapper are enforced
  by `clippy.toml`.

## 8. Language Design

The spec chapters were read by an agent. I checked each rule quoted below
against its `r[…]` definition.

### Goals And Where They Diverge

| Language goal (source) | Compiler goal | Relation |
| --- | --- | --- |
| "Every signature is explicit, so an agent reads a header, never a body" (README) | parallel, incremental | Conflict: `fn.decl.result-omitted-private` and `req.row.omitted.inferred-private` infer from bodies. |
| Explicit over inferred, no action at a distance (`docs/future-work/README.md`) | incremental | Aligned: `module.package.no-inference` keeps bodies out of interfaces. |
| Capabilities for time, randomness and I/O (README) | artifact quality | Aligned; host calls cost 6.7 to 33 µs against targets of 1 to 10 µs. |
| Derive from types, no macros (README) | fast | Aligned; template bodies enter `check` keys as text hashes. |
| Representation is unobservable (`types.generic.unobservable`) | full monomorphization | Diverges: `req.poly.one-body` fixes one body per row. |
| Definite initialization follows calls and dispatch (`module.init.definite.whole-module`) | incremental, fast | Costs a per-body summary of every reachable impl method (F11). |

### Decisions That Constrain The Compiler

| Rule | Costs | Buys |
| --- | --- | --- |
| `module.cycle.acyclic`, the folder as interface unit | a use-closure key per module | parallel checking with no cross-folder fixpoint |
| `fn.decl.result-omitted-private`, `req.row.omitted.inferred-private` | a serial pass per module, a row fixpoint | less typing in private code |

### Questions For The Owner

Options run from the cheapest kind of change in the Design Cost Order.

1. **Should private functions keep inferred results and rows?**
   (a) Keep the rule and fix the compiler: an explicit stack, and a
   parallel pass. (b) Require `-> T` and the `$` row on every named
   function, with a fix-it that writes them; closures and local `fn` still
   infer. Option (b) removes a rule and adds none. Rust and Go require
   full signatures on private functions.
2. **Is 64 the right fixed proof depth?** (a) Keep it and cap the metric
   fixture at 63 adapters. (b) Raise the number. (c) Stop counting a
   subgoal already proven for the inner receiver, which is a rule
   exception.
3. **Which generic-body rule stands?** `types.generic.interfaces` says
   interfaces carry the bodies downstream compilation needs.
   `module.interface.generic-bodies` says downstream "must not require
   them".
4. **Which resource record is current?** `goals.md` says resources use
   `Disposable` and `using`. `shared-rules.md` says not to propose `using`.
   `lex.defer.identifier` makes `defer` an ordinary identifier, while
   `goals.md` describes a `defer` suite.
5. **May doc tests of one package share a program?** A6 shows the cost is
   the engine, so this now ranks last. Rust merged doctests in the 2024
   edition for compile time
   ([edition guide](https://doc.rust-lang.org/edition-guide/rust-2024/rustdoc-doctests.html)).

Other items the spec read found, each unverified beyond the rule text:
`data.repr.gc` says composite values "are garbage collected", which names
a mechanism; eight rules in chapter 13 reject forms with
`references-not-yet-checked`; six limits are implementation-defined while
`trait.bound.depth.fixed` argues that limits should be fixed.

## 13. Checker, TIR, Ownership And Reference Counting

A second pass over four connected designs, for both architecture and
implementation. Sources: `crates/hd_check/DESIGN.md`,
`docs/compiler/tir-v2.md`, `crates/hd_tir/src/own.rs`,
`crates/hd_driver/src/own.rs`, the emitter's counting modules,
`crates/hd_wasm/DESIGN.md` §23, and the ownership records in
`docs/future-work/`. An agent gathered the facts and I reread each code
site cited below.

### Verdict

Revised on 2026-11-12 after the owner challenged the first version, which
leaned on the design records and had not read the emitter.

**It works when run.** Eight leak probes held memory flat from 100,000 to
400,000 iterations, in dev and release, with equal output. Append and
push loops are linear, and cycles are collected. The suites are large,
and conformance has no known failure.

**It is not the design the records describe, and it is not simple.**
In the code, counts and loans are decided in six layers, about
54,000 lines, and only one layer has a static verifier. The checked
build audits a module that differs from the shipped one at ten or more
emission sites. Correctness therefore rests on tests, not on structure.

**The checker is the weaker part.** Most defects of §5 are in it, and its
failures are silent: a wrong answer or a crash, with no diagnostic.

### What Works When Run

Four consequences:

- **No one place shows a body's final counts.** The `counts` stage view
  reads emitted code, which is why it exists.
- **The static verifier covers one row.** `verify_owned` checks TIR after
  the passes. Counts the emitter adds and the peephole deletes are not
  checked statically.
- **The checked build is not the shipped build.** Emission branches on it
  at ten or more sites. It turns off inlined counts
  (`module.rs:2024`), uses `Helper::New` where a normal build uses the
  `NewFixed` small-block path (`emit/value.rs:224`), and swaps the
  runtime for `std.rt.checked`. Those paths are covered only by output
  comparison.
- **The emitter's count files are still changing.** `emit/count.rs` and

  stages closed.

instance can disagree on who owns an argument.

### Architecture Risks

**R1. The pipeline has outgrown its stated constraints.**

`tir-v2.md` designed six passes run once per generic body, over an
`OwnCx` of three signature facts, with no cross-function analysis, each
pass only weakening what insertion wrote. Its "As built" section now
records the code: about 21 steps per instance, about 45 `OwnCx` methods,
the inliner and release summaries, a whole-program loan pass, and steps
after the splice that add statements.

Three consequences follow **[V]**:

- A function's emitted code depends on inlined callees, callee summaries,
  promoted arguments and link-time loan tables. The cacheable unit of
  direction 1 is therefore larger than a function.
- The dev pipeline is not free of optional passes (§4 A5).
- The safety argument "`copy` is always sound, and later passes only
  weaken" covers `insert` to `hoist`. It does not cover the later TIR
  steps that add statements, nor the emitter and the peephole.

**R2. The verifier is not independent.**

- `verify_owned` runs once, after the whole pipeline, and only in a debug
  compiler or a checked build (`hd_driver/src/lib.rs:3647`) **[V]**. A
  release `hd` does not run it.
- It shares `own::operands`, `consumes_counts` and `OwnCx` with the passes
  (`hd_tir/src/ir/owned.rs:70`), so a wrong consumer classification is
  wrong in both (agent, read).
- "Correct after any prefix" is stated (`own.rs:27`) and no test runs a
  prefix (agent).
- Loan elision has no dynamic backstop. `POINTER_LOANS.md` (git history at 7ccbb4ea8) says "a loan
  wrongly elided is a freed read, with no panic".

Swift keeps a separate ownership verifier for the same reason.

**R3. Per-instance ownership.** Pass work grows with instances, not with
generic bodies. The 4,096-leaf fallback is a cliff: a larger type gets
the conservative generic body **[I]**.

**R4. Run-time loans are per object.** Writing one field through an alias
while a reference to another field is live panics:

```text
fn rename(t: &Team, alias: *mut User) -> void $ Console:
    n := &t.lead.name
    alias.age += 1
    println(*n)
```

With `alias` equal to `t.lead` this prints `panic: borrow-conflict` in dev
and release **[V]**. The rule is `ref.excl.alias.conflict`, and it covers
only `*T`. Rust's `RefCell` behaves the same.

**R5. The collector is synchronous.** `collect` is one loop over every
candidate, triggered when live candidates reach a threshold that starts
at 10,000 and doubles or halves (`lib/std/rt/cycle.hd:81`, `:211`). No
pause bound exists, and the daily `long-run-memory` line reports no
pause figure.

**R6. No static reuse.** Nothing like Perceus reuse tokens or drop
specialization exists in `hd_tir/src/own/`; `REFCOUNT_RUNTIME.md` §4.3 (git history at 7ccbb4ea8)
lists it as taken (agent). Run-time uniqueness covers the common loops.
One idiom stays quadratic, though std already has the linear form
(`std-collections.map.get-or-insert`):

| Loop body, one key | 80,000 | 160,000 | 320,000 |
| --- | --- | --- | --- |
| `xs = m.get(0).unwrap_or([])`, `xs.push(i)`, `m[0] = xs` | 0.76 s | 1.58 s | 6.35 s |
| `m.get_or_insert(0, []).push(i)` | 0.05 s | 0.05 s | 0.05 s |
| `xs = m.remove(0).unwrap_or([])`, `xs.push(i)`, `m[0] = xs` | 0.05 s | 0.05 s | 0.07 s |

All **[V]**, wasmtime, `--release`. `get` returns a copy that shares the
list's buffer with the map. The push then finds two holders and copies
the buffer, once per round. `remove` leaves one holder, so the push is in
place.

### The Checker And TIR

The checker is fast on ordinary code and passes 3,692 typing cases. It is
not robust. Of the defects in §5, the silent depth caps,
all three exponential cases (F8, F9, F16)
and three of the cost defects (F10, F14, F15) are in `hd_check` or the
unifier it drives. Its own tests are 22 unit tests and 108 stage cases,
so scale and depth are untested. The design choices behind this:

- **One pass checks and lowers.** The checker writes TIR through
  `TirSink` while it types each expression (`hd_check/DESIGN.md` §1.5).
  This is fast: 182 ms for 10k lines. The costs are three. Every trial
  must roll emitted TIR back. Lowering code for loops, references and
  coercions lives in the checker. The designed no-emit mode is not
  built, so `--fix` rounds and the playground build and verify TIR they
  never use (the record says so).
- **Types are walked as trees.** Promise 4 of §1.5 lets instructions
  carry inference variables until the end of the body. `resolve` and
  `fold_vars` then walk each type as a tree, though the pool stores a
  DAG. That is F8 and F14. `MAX_INSTANCE_LEAVES` in the driver guards
  the same blow-up on the ownership side.
- **Limits answer silently.** The 16 unexercised caps are
  checker walks. F16 is exhaustiveness with no fuel.
- **Structured IR needs a topology.** `own::run` rebuilds it five times
  per body, which is linear. Building it per closure in the emitter is
  F20.
- **Three layers rewrite code.** TIR, owned TIR and the Wasm `Ins` list.
  `tiering.md` says passes never rewrite TIR.

## 14. Suggestions: TIR, Emitter, Opt And Checker

Proposals only. Each names its evidence in this file, the prior art, and
a rough cost. They assume the owner's answer of 2026-11-12 that
cross-function analysis is allowed.

### The Shape Underneath

Three of the four areas share one cause. The emitter lowers each TIR
value to a fresh Wasm local and to linear stack code. Everything after
that must recover structure from a stack machine: 19 peephole rules,
count deletion by dataflow, and whole-module passes. So optimization and
ownership decisions land at the level that knows least.

The suggestion that follows from this: **decide on an instance form that
has layout in view, lower once, and keep the Wasm level to encoding.**
The first version of this section said "decide in TIR". The owner
corrected that; see "Owner Correction" below.

### Owner Correction, 2026-11-12: TIR Has No Instantiation

Owner: "TIR really cannot decide ownership/count/loan, it does not have
generic instantiation." The code agrees **[V]**:

| Where instantiation happens | Site |
| --- | --- |
| The driver clones a body per instance, substitutes its types and re-chooses impls, before the passes | `hd_driver/src/own.rs:2377` (`map_body_types`, `inline::rechoose`) |
| The emitter substitutes again, one type per instruction | `Em::inst_ty`, from `hd_mono::instruction_types` (`hd_wasm/src/emit.rs:1532`) |
| A generic local function stays generic inside its body until emission | `sub_flags::GENERIC`, `Body::is_instantiation` (`hd_tir/src/ir.rs:1241`) |
| Past 4,096 type leaves no instance body is made; the generic body serves | `hd_driver/src/own.rs:112` |

`Body` itself has no instance: no instance id, no type arguments, no
layout. Layout lives in `hd_mono/src/layout.rs` and
`hd_wasm/src/layout.rs`, above `hd_tir` in the crate order. The passes
reach it only through the 45 callbacks of `OwnCx`.

So three kinds of decision cannot be made in TIR as it stands:

- **By layout.** How many counted leaves a value has, and whether an
  argument is passed owned (`layout::function_pass`, used by
  `Em::argument_pass`, `emit.rs:3034`).
- **By instance.** Counts in a generic local function, and in any
  instance over the leaf limit.
- **By storage.** Loans, which read instance and layout facts
  (`emit/loan_facts.rs`).

This makes the emitter's decisions necessary today, not accidental. The
finding of §13 stands in a narrower form: those decisions have no static
verifier.

Two ways forward, for the owner:

| Option | What changes | Cost | Buys |
| --- | --- | --- | --- |
| A. Keep TIR generic and accept emission-time decisions | Record that the emitter decides by layout and instance. Keep count and loan operations symbolic in the emitted list until link, and verify balance there. Drop T3. | low | a verifier and a bisect point where the decisions are made |
| B. One instance form (T1) | `hd_mono` builds it once: substituted, impls chosen, local generic functions instantiated, layout attached. The passes run on it; the emitter only lowers. | high | one place for every count and loan; a cache unit; the three substitution sites become one |

Rust takes a third path: drops are placed in generic MIR, and only the
action of dropping a `T` is resolved per instance, as drop glue.
`tir-v2.md` chose that at first ("count operations stay symbolic, and the
emitter drops them for scalar instances"). The per-instance summaries of
release builds have already left it.

My recommendation is A now and B when direction 1 is taken up, since B's
instance form is also the cache unit that direction needs.

### Generic Or Instance TIR?

Owner question, 2026-11-13. Recommendation: keep both, and give each one
job. This is option B above, stated as a target.

| Form | Job | Never does |
| --- | --- | --- |
| Generic TIR | the checker's output; the unit of the `check` cache; what a dependent package instantiates | ownership, counts, loans, layout |
| Instance TIR | one per instance, built once in `hd_mono`; the unit of ownership, optimization, emission and code caching | anything a dependent reads |

Reasons:

- **hd has no optimizer after emission.** Rust decides drops in generic
  MIR because LLVM optimizes each instance afterwards. hd's passes are
  the only optimizer, so they need concrete types and layout.
- **The code is already there in fact.** The driver builds an instance
  body, the release summaries are per instance, and `hd_mono` keeps
  `instance_bodies`. What is missing is one builder and a name.
- **Swift and Go do the same.** Swift keeps generic SIL and runs its
  ownership optimizer on specialized functions. Go keeps generic IR and
  stencils per shape before SSA.
- **A non-generic function costs nothing extra.** Its instance form is
  its generic form.

Three guards against the cost, which grows with instances:

1. Key the instance form by layout shape where two instances share one,
   as Go does by GC shape.
2. Cache it by the generic body's hash, the shape key, and the callee
   facts it read. That entry is direction 1's code cache.
3. Memoize layout by type id (T4), so the 4,096-leaf fallback can go.

Use the same column encoding with a phase mark, not a new IR. The
verifier then rejects a type parameter, an unchosen impl or a generic
local function in an instance body.

### Order

1. **C3, C6, C7, T4.** They remove wrong answers and crashes, and
   each is small.
2. **O2, O3, O6, C8.** Tools and tests that make the rest safe to change.
3. **E2, then T1.** A per-function cache and parallel finish, then the
   instance form as the cache unit.
4. **E1, then O4.** Stackify at emission, then retire the peephole rules
   it makes dead.
5. **T3, E3.** Counts and loans as statements of the instance form, and
   a checked build that emits shipped code. T3 needs T1.
6. **T6, C1, C2.** Suspension size, parallel body checks, method choice.

### What I Would Not Change

- Structured control flow in TIR. It fits Wasm, and no pass here needs a
  CFG.
- The flat column encoding and the hand-written wire form.
- Run-time uniqueness for in-place update. The probes of §13 show it
  works, and static reuse would add a seventh layer.
- One pass for checking and lowering (C9).
